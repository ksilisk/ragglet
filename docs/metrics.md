# Метрики

Как ragglet оценивает качество выдачи и производительность: что значит каждая метрика, как
она считается и чем наши цифры отличаются от BEIR. Настраиваются метрики в `metrics`
сценария (см. `docs/config-reference.yaml`). Задержки и пропускная способность — в разделе
[«Задержки и пропускная способность»](#задержки-и-пропускная-способность), попадания в кэш —
в разделе [«Кэш»](#кэш).

## Откуда берётся «правильный ответ»

У датасета есть разметка `qrels/<split>.tsv`. Каждая строка в ней говорит: «для запроса Q
документ D имеет оценку N». Оценку ставил человек.

| Оценка | Что значит | Для метрик |
|---|---|---|
| 2, 1, … (больше 0) | документ по теме; чем больше, тем полезнее | **нужный** |
| 0 | человек посмотрел и решил: не подходит | ненужный |
| меньше 0 (бывает в некоторых датасетах) | точно не подходит | ненужный |
| документа нет в разметке | его никто не оценивал | ненужный |

**Документ нужный, если его оценка больше 0.** Величину оценки учитывает только `ndcg`.
Для остальных метрик 2 и 1 одинаково значат «нужный».

## Сквозной пример

Для запроса нужны четыре документа: **A** и **D** с оценкой 2, **B** и **C** с оценкой 1.
Система вернула **X, B, A, Y, C** (X и Y не нужны, D не найден). «@5» значит: смотрим на
первые 5 мест.

| Метрика | На какой вопрос отвечает | В примере, @5 |
|---|---|---|
| `hit` | Нашли ли хоть один нужный документ? | да → **1** |
| `recall` | Какую долю нужных нашли? | 3 из 4 → **0.75** |
| `r_cap` | Как recall, но делим не больше чем на число мест | 3 из min(5, 4) → **0.75** |
| `precision` | Какая доля выдачи полезна? | 3 из 5 мест → **0.6** |
| `mrr` | Как высоко стоит первый нужный? | на 2-м месте → 1/2 = **0.5** |
| `ndcg` | Насколько хорош порядок с учётом оценок? | **0.48** |

Все метрики лежат в диапазоне от 0 до 1, больше значит лучше. В summary каждая
усредняется по запросам (`<колонка>_mean`), в агрегате — по повторам.

Если поменять местами A и B (**X, A, B, Y, C**), изменится только `ndcg` (0.48 → 0.51):
нужные документы те же и первый нужный по-прежнему на 2-м месте. Важный документ подняли
выше, и это видит только nDCG.

## nDCG

1. Каждый найденный документ приносит **очки, равные своей оценке** (2, 1 или 0).
2. Чем ниже место, тем меньшая доля очков засчитывается:

   | место | 1 | 2 | 3 | 4 | 5 | … | 10 |
   |---|---|---|---|---|---|---|---|
   | засчитывается | 100% | 63% | 50% | 43% | 39% | … | 29% |

3. Сумма — это очки системы.
4. Очки **идеальной выдачи**: все нужные документы, от важных к менее важным, на тех же k
   местах. Это максимум, который можно набрать.
5. **nDCG = очки системы / максимум.** 1.0 означает идеальный порядок.

В примере: система набрала 0 + 1·63% + 2·50% + 0 + 1·39% ≈ 2.02, идеал **A, D, B, C**
даёт 2·100% + 2·63% + 1·50% + 1·43% ≈ 4.19, nDCG@5 = 2.02 / 4.19 ≈ 0.48.

На датасете с оценками только 0/1 nDCG всё равно полезен: он поощряет нужные документы
на верхних местах.

## r_cap

recall бывает ограничен сверху самим датасетом. В nfcorpus у запроса в среднем около 38
нужных документов, и даже идеальная выдача @10 даст recall 10/38 ≈ 0.26. `r_cap` делит не
на число нужных, а на min(k, число нужных) и в этом случае показывает 1.0. Если нужных
меньше k, `r_cap` совпадает с `recall`, если больше — с `precision`.

## Документы и чанки

Документы в индексе нарезаны на чанки, система возвращает чанки. Метрики считаются на
двух уровнях:

- **doc** (`metrics.quality.doc`): чанки переводятся в документы. Документ занимает место
  своего лучшего чанка, а повторы этого документа ниже по списку пропускаются. Так один
  документ не приносит очки дважды, и nDCG не может превысить 1. Цифры этого уровня
  сравнимы с BEIR.
- **chunk** (`metrics.quality.chunk`, по умолчанию выключен): каждый уникальный чанк
  финального списка — отдельное место, нужность наследуется от документа. Уровень
  показывает, какая доля контекста полезна. Включайте его, если сценарий варьирует
  chunking или context. При `chunking.method: none` уровни совпадают.

`recall`, `r_cap` и `ndcg` доступны только на уровне doc: для них нужно знать, сколько
нужных единиц существует всего, а разметка есть только по документам. Конфиг с ними в
`metrics.quality.chunk` не пройдёт валидацию.

## Граничные случаи

- **Запрос без нужных документов** (в разметке только оценки ≤ 0) исключается из оценки.
  При загрузке датасета на каждый такой запрос выводится предупреждение
  `qrels.no_relevant`.
- **Запрос без ответа** (таймаут или ошибка генерации) и **пустая выдача** (пустой индекс):
  финальный список пуст, все метрики 0, запрос засчитан как промах. Для запроса без ответа
  это верно на любом этапе, даже если поиск успел найти нужное. Подробнее в разделе про
  задержки.
- **В выдаче меньше k документов** (например, 30 чанков дали 18 документов): @k считается
  по более короткому списку. Доля таких запросов — `doc_short@<k>_rate` в summary.
  Каждое `k` не может превышать глубину финального списка, это проверяется при загрузке
  сценария.

## Сравнение с BEIR и MTEB

BEIR и MTEB считают метрики через pytrec_eval (trec_eval). Наши формулы совпадают с ними.
Unit-тесты сверены с pytrec_eval, в nDCG очки равны оценке, как в `ndcg_cut`.
Расхождения возможны в трёх местах:

- **Запросы без нужных документов.** BEIR оставляет их и ставит нули по всем метрикам, мы
  их исключаем. На таких датасетах наше среднее будет чуть выше опубликованного;
  предупреждение `qrels.no_relevant` показывает, есть ли такие запросы.
- **Одинаковый score.** pytrec_eval переставляет такие документы по имени, мы берём порядок
  финального списка (после rerank и context).
- **Сам поиск.** У нас приближённый поиск Qdrant (HNSW) и чанкинг; опубликованные
  результаты обычно получены точным поиском по документам целиком.

## Задержки и пропускная способность

Итоги считаются на каждый повтор (`run.repeats`) и только из строк `per_query`, поэтому
summary всегда можно пересчитать по ним.

### Исход запроса

У каждой строки есть `outcome`:

| `outcome` | Что значит |
|---|---|
| `ok` | ответ: запрос дошёл до конца, выдача есть, а при включённой генерации есть и ответ LLM |
| `timeout` | запрос не уложился в `timeouts.total_ms` или в бюджет этапа; этап записан в `timeout_stage` |
| `error` | генерация вернула ошибку, текст в `generation_error` |

Ошибка стенда (Qdrant недоступен, баг в коде) останавливает прогон и в строки не попадает.

### Пример

Бюджет `timeouts.total_ms: 300`, модель нагрузки `closed` с `concurrency: 2`, шесть
запросов, в сценарии есть реранк. Время в миллисекундах от начала повтора.

| запрос | старт (`t_start_ms`) | эмбеддинг | поиск | реранк | конец | `outcome` |
|---|---|---|---|---|---|---|
| A | 0 | 10 | 20 | 70 | 100 | `ok` |
| B | 0 | 20 | 30 | 70 | 120 | `ok` |
| C | 100 | 10 | 20 | 120 | 250 | `ok` |
| D | 120 | 20 | пусто | пусто | 420 | `timeout` |
| E | 250 | 10 | 20 | 90 | 370 | `ok` |
| F | 370 | 10 | 20 | 60 | 460 | `ok` |

D посчитал эмбеддинг, но поиск не ответил, и через 300 мс запрос упёрся в бюджет.

| Итог повтора | Значение | Откуда |
|---|---|---|
| `n` | 6 | все запросы датасета |
| `ok_count` / `timeout_count` / `error_count` | 5 / 1 / 0 | по `outcome`, в сумме всегда `n` |
| `wall_ms` | 460 | от начала повтора до конца последнего запроса |
| `throughput_qps` | 10,9 | 5 ответов за 0,46 с |
| `lat_total_p50` / `lat_total_p95` | 120 / 262,5 | по всем шести, D входит со своими 300 мс |
| `lat_rerank_p50` | 70 | по пяти запросам, где реранк завершился |
| качество D | 0 | ответа нет, промах |

### Правила подсчёта

- **Время повтора** `wall_ms` — от начала повтора до конца последнего запроса. В строке
  `t_start_ms` — старт запроса (плановый момент модели нагрузки) от начала повтора, конец —
  `t_start_ms + lat_total_ms`. По этим колонкам видно, сколько запросов шло одновременно.
- **Пропускная способность** `throughput_qps` — **только ответы** (`ok`) в секунду времени
  повтора. Таймаут и ошибка в неё не входят: система их обработала, но пользователь ничего
  не получил. Иначе перегруженная конфигурация с таймаутами выглядела бы не хуже здоровой.
  Сколько запросов обработано всего, видно из `n` и `wall_ms`.
- **Общая задержка** `lat_total` — **по всем запросам**, вместе с таймаутами и ошибками:
  сколько пользователь ждал любого исхода. Если выкинуть таймауты, при перегрузке самые
  медленные запросы выпадали бы из подсчёта, и p95 «улучшался» бы с ростом нагрузки.
- **Задержка этапа** `lat_<этап>` — **только там, где этап завершился**. Если этап прерван
  таймаутом, упал, не был достигнут или выключен, ячейка пустая и в перцентили не входит.
  Ноль был бы значением и выглядел бы самым быстрым запросом. По заполненным ячейкам видно,
  докуда дошёл запрос с таймаутом. Этап, выключенный в сценарии, даёт в summary `null`.
- **Качество** — запрос без ответа (`timeout` или `error`) засчитывается **промахом**:
  финальный список пуст, все метрики 0, на каком бы этапе запрос ни остановился. Из
  среднего он не исключается, поэтому у прогонов одного датасета один и тот же набор
  запросов. Если исключать, качество перегруженного прогона зависит от того, какие запросы
  выжили, и может оказаться выше, чем без нагрузки. Чистое качество ранжирования меряйте
  без таймаутов: `timeout_rate` в summary равен 0.

Перцентили считаются точно по строкам, с линейной интерполяцией (см. справку). В агрегате по
повторам для каждого итога — среднее, стандартное отклонение, минимум и максимум; p95 там —
средний p95 повтора.

### Как читать

- **Сравнение уровней нагрузки** — прогоны одного сценария с разным `run.load`.
  `compare_runs` должен показывать только это различие.
- **Перцентиль упёрся в бюджет.** Если доля таймаутов больше 1 − p/100, `lat_total_p<p>`
  попадает на таймауты и примерно равен бюджету. Это значит «не меньше бюджета», а не
  измеренную задержку.
- **Хвост повтора.** В конце повтора воркеры освобождаются по одному, поэтому
  `throughput_qps` занижен примерно на concurrency / (2n). Если `concurrency` не больше
  n/20, искажение меньше 2,5%.
- **p99 на сотнях запросов** определяют несколько самых медленных запросов. Смотрите
  разброс по повторам.
- **Кэш** влияет на задержки, его попадания и промахи разобраны в разделе
  [«Кэш»](#кэш).

## Кэш

В сценарии можно включить два слоя кэша (`cache`): кэш retrieval в памяти (LRU) и кэш
эмбеддингов в Redis. Запрос сначала ищет готовую выдачу в кэше retrieval. Если нашёл,
эмбеддинг и поиск пропускаются. Если нет, вектор берётся из кэша эмбеддингов или считается
моделью, потом идёт поиск.

### Отметки у запроса

| Колонка | Значения |
|---|---|
| `ret_cache` | `hit` — выдача из кэша retrieval, `miss` — её там не было, пусто — к кэшу не обращались |
| `emb_cache` | то же для кэша эмбеддингов |

Пусто бывает, когда слой выключен, запрос упёрся в таймаут до обращения к кэшу, или, для
`emb_cache`, выдачу уже дал кэш retrieval. Если кэш спросили, а потом запрос упал по
таймауту, отметка остаётся. При попадании в кэш retrieval `lat_embed_ms` пустая: этап не
понадобился, а `lat_retrieve_ms` — время поиска в LRU.

### Итоги повтора

Для каждого включённого слоя, `emb` и `ret`. У выключенного слоя полей в summary нет.

| Итог | Что значит |
|---|---|
| `<слой>_hits`, `<слой>_misses` | сколько запросов попали в кэш и сколько промахнулись |
| `<слой>_hit_rate` | hits / (hits + misses); пусто, если к кэшу ни разу не обращались |
| `lat_total_<слой>_hit_p<P>` | перцентиль `lat_total_ms` по запросам, попавшим в кэш |
| `lat_total_<слой>_miss_p<P>` | то же по промахам |

Доля считается по счётчикам. Пример: в namespace лежат векторы трёх запросов из шести,
потому что заполняющий прогон остановили на середине. Прогон по всем шести даёт
`emb_hits` 3, `emb_misses` 3 и `emb_hit_rate` 0,5 при любом порядке запросов и любой
конкурентности. Таймаут после обращения к кэшу входит в свой срез задержки, как и в
`lat_total`.

### Как читать

- **Повторы.** Каждый повтор начинается с кэша в том же состоянии, что на старте прогона:
  кэш retrieval очищается, свои ключи Redis удаляются. Поэтому повторы отличаются только
  шумом. Холодный и тёплый кэш — это разные прогоны: тёплый старт кэша эмбеддингов даёт
  второй прогон с тем же `cache.embedding.namespace`.
- **Кэш retrieval на датасетах с уникальными текстами не попадает.** LRU очищается перед
  каждым повтором, а внутри повтора запросы не повторяются. `ret_hit_rate` равен 0, и
  прогон с LRU показывает только его накладные расходы.
- **Доля меньше 1 на тёплом старте** значит, что namespace заполнен не целиком. Заполняющий
  прогон не дошёл до конца, шёл по другим запросам или с меньшим `dataset.limit`, или часть
  ключей истекла по `ttl_seconds`.
- **Устаревших значений в кэше не бывает.** Ключ кэша эмбеддингов содержит модель, её
  ревизию и `normalize`. Кэш retrieval живёт один повтор, а индекс за время прогона не
  меняется.

## Справка: формулы

Места нумеруются с 1, после перевода в документы (или после схлопывания одинаковых
чанков на уровне chunk). `rel(i)` — оценка на месте i (0 для ненужных), `R` — нужные
документы запроса.

| Метрика | Формула |
|---|---|
| `hit@k` | 1, если среди первых k есть нужный, иначе 0 |
| `recall@k` | (нужных среди первых k) / \|R\| |
| `r_cap@k` | (нужных среди первых k) / min(k, \|R\|) |
| `precision@k` | (нужных среди первых k) / k |
| `mrr@k` | 1 / (место первого нужного), 0 если его нет среди первых k |
| `ndcg@k` | DCG@k / IDCG@k, где DCG@k = Σ_{i ≤ k} rel(i) / log2(i + 1), а IDCG@k — то же для оценок из R по убыванию; 0, если R пусто |

Производительность одного повтора: строки i = 1..n, `s_i` — `t_start_ms`, `L_i` —
`lat_total_ms`.

| Итог | Формула |
|---|---|
| `<outcome>_count` | число строк с этим `outcome` |
| `<outcome>_rate` | `<outcome>_count / n` |
| `wall_ms` | max_i (s_i + L_i) |
| `throughput_qps` | `ok_count / (wall_ms / 1000)` |
| `lat_total_p<P>` | перцентиль P по L_i всех строк |
| `lat_<этап>_p<P>` | перцентиль P по непустым `lat_<этап>_ms` |
| `<слой>_hits`, `<слой>_misses` | число строк, где `<слой>_cache` равна `hit`, `miss` |
| `<слой>_hit_rate` | hits / (hits + misses), пусто при hits + misses = 0 |
| `lat_total_<слой>_<hit\|miss>_p<P>` | перцентиль P по L_i строк с этой отметкой |

Перцентиль — `Series.quantile(P / 100)` в pandas, линейная интерполяция (как
`numpy.percentile` по умолчанию). В примере значения `lat_total_ms` по возрастанию: 90,
100, 120, 120, 150, 300; p95 стоит на позиции 0,95 · 5 = 4,75, между 150 и 300:
150 + 0,75 · 150 = 262,5.
