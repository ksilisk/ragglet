# ragglet-25 — [Э3/C2] Улучшение merge и дедупликации

**Статус: предложение для обсуждения; этот PR содержит только дизайн.**
Анализ опирается на код `4793017`. Задача — сделать слияние результатов
настраиваемым и предсказуемым, проверить ранжирование и экспериментально
обосновать выбор метода для одиночного, гибридного и распределённого поиска.

Предлагается сохранить RRF по умолчанию, открыть настройки нормализации и
взвешенного interleave, исключить повторный вклад одного чанка внутри источника
и отделить исходный score от результата слияния. Для однородных шардов отдельно
проверить `weighted_sum` без нормализации: локальный ранг и локальный min-max
могут терять информацию, нужную для глобального ранжирования.

## Проблема на простом примере

Пусть два непересекающихся шарда используют одну модель и сопоставимые scores.
Чанки принадлежат разным документам; релевантны только `a` и `b`.

| Источник | Локальный ранг 1 | Локальный ранг 2 |
|---|---|---|
| A | `a`: 0,90 | `b`: 0,89 |
| B | `c`: 0,20 | `d`: 0,10 |

При равных весах RRF с `rrf_k=60` даёт `a` и `c` одинаковый score `1/61`,
а `b` и `d` — `1/62`. Получаем `a, c, b, d`: слабый `c` опережает сильный `b`.
Точный min-max отдельно по источникам тоже даёт `a=1, c=1, b=0, d=0`.
В текущем коде добавка epsilon к знаменателю чуть понижает максимум более узкого
диапазона: `a≈0,99999990`, `c≈0,99999999`, поэтому `c` оказывается первым.
Сумма исходных scores сохраняет порядок `a, b, c, d`.

| Метод в текущем коде | Первые два чанка | Recall@2 | nDCG@2 |
|---|---|---:|---:|
| RRF | `a, c` | 0,5 | 0,6131 |
| Weighted sum / minmax | `c, a` | 0,5 | 0,3869 |
| Weighted sum / none | `a, b` | 1,0 | 1,0 |

Это вычислимый пример, **не замер S5**.
Он показывает возможную причину деградации; влияние приближённого поиска,
состава кандидатов и конфигурации нужно отделить экспериментом.
В репозитории есть сценарий S5, но рассмотренные материалы не дают достаточно
данных для количественного вывода о его деградации.

Для vector + BM25 предположение о сопоставимых исходных scores уже не подходит.
Поэтому универсально заменить RRF на сумму scores нельзя: выбор зависит от
смысла источников, а не только от числа backend.

## Контракт слияния

Вход — упорядоченные выдачи источников. Сохраняем порядок, полученный от backend:
merge не пересортировывает его по raw score. Для weighted sum поддерживаемый
контракт scores — «больше означает лучше». В текущей схеме индекса есть `euclid`,
у которого меньшее расстояние лучше ([документация Qdrant](https://qdrant.tech/documentation/search/#filtering-results-by-score)).
Поэтому preflight проверяет фактическую метрику коллекции и отклоняет weighted
sum с Euclid или неизвестным направлением score для обеих нормализаций.
RRF/interleave используют готовые ранги и не требуют такого ограничения.
Преобразование расстояний с сохранением raw score можно добавить отдельно;
молчаливо считать Euclid сходством нельзя.

Для `fanout_merge` выполняются следующие шаги:

1. Проверить идентификаторы и конечность scores. Пустые `chunk_id`/`doc_id`,
   `NaN` и бесконечности — ошибка данных, а не молчаливое исключение кандидата.
2. Внутри каждого источника оставить первое появление `chunk_id`, перенумеровать
   ранги с 1. Один источник даёт одному чанку не больше одного вклада.
3. Выполнить выбранное слияние. Порядок источников всегда берётся из snapshot,
   включая последовательный режим и любой порядок завершения async-запросов.
4. Применить правила повторов для метода и затем ограничить список `top_k`.
   Если доступно меньше кандидатов, вернуть фактически доступные.

Проверка повторов выполняется до нормализации: иначе дубли меняют статистику
источника. При одинаковом `chunk_id`, но разных `doc_id` или текстах чанка
выдача некорректна и отклоняется. Сравниваем `doc_id` и `payload.text`;
отсутствующий и присутствующий текст также считаются различием.
Другие поля payload и `point_id` могут различаться. Представитель выбирается
по минимальному локальному рангу, затем индексу источника в конфигурации,
затем `point_id`. Raw scores разных источников для этого не сравниваем.

Для RRF и weighted sum сортировка: итоговый score по убыванию, лучший локальный
ранг по возрастанию, индекс источника этого появления, затем `chunk_id`.
Суммирование идёт в фиксированном порядке источников; при численном переполнении
возвращается явная ошибка. Одинаковый вход должен давать одинаковый выход.

### RRF

Для чанка `c`:

```text
score_fused(c) = sum(weight[s] / (rrf_k + rank[s,c]))
```

Суммируем только по источникам, содержащим чанк. Ранги начинаются с 1.
`rrf_k >= 1`, default 60. Нулевой вес не даёт вклад и не добавляет кандидата.
Общий множитель всех положительных весов меняет scores, но не порядок.
RRF остаётся baseline для источников с несопоставимыми шкалами.
Два одинаковых логических источника всё ещё дают два голоса: автоматического
распознавания реплик нет; число источников и веса должны быть осознанными.

### Weighted sum

```text
score_fused(c) = sum(weight[s] * normalize_s(score_raw[s,c]))
```

Отсутствие чанка в источнике даёт нулевой вклад. Нормализация выполняется для
одного запроса внутри одной выдачи после удаления локальных повторов.

| `normalize` | Правило | Когда проверять |
|---|---|---|
| `minmax` (default) | `(x - min) / (max - min)`; при диапазоне `<= 1e-9` все значения равны 0 | Гибридные источники с разными шкалами. |
| `none` | `x` без преобразования | Шарды с общей моделью, метрикой и шкалой scores. |

Пустая выдача не участвует в нормализации. Единственный кандидат и константный
список в min-max получают 0: внутри списка нет информации для различения scores.
Это явный компромисс, а не оценка нерелевантности; порядок таких кандидатов
определяется правилом равенства, а RRF служит альтернативой для коротких выдач.
Кандидаты с нулевым итоговым score сохраняются; только источник с весом 0 исключён.
Для `none` допустимы отрицательные scores. Нулевой вклад отсутствующего источника
может превосходить отрицательный вклад присутствующего — это фиксируется тестом
и учитывается при выборе метода для перекрывающихся выдач.

`zscore` не добавляем в первую реализацию: он вводит отрицательные вклады,
зависит от дисперсии короткого top-k и требует отдельного обоснования обработки
отсутствующих кандидатов. Упоминание «позже» в текущем коде не является поддержкой.
Min-max тоже не калибрует вероятность релевантности и чувствителен к глубине выдачи.

### Interleave

По умолчанию сохраняется round-robin: один следующий доступный кандидат на
источник в порядке конфигурации. Взвешенный режим выбирается явно.

Для weighted interleave используем smooth weighted round-robin вместо квот:
текущие счётчики источников начинают с 0; перед каждым выбором прибавляем вес
каждого доступного источника, выбираем максимальный счётчик и вычитаем из него
сумму весов доступных источников. Равенство разрешается индексом источника.
Пример для весов 2:1 при достаточных непересекающихся списках: `A, B, A, A, B, A`.

Перед выбором пропускаем уже выданные чанки, если включена дедупликация.
Источник без допустимого кандидата удаляем из доступных до пересчёта весов;
пропуск дубля не расходует ход. Нулевые веса исключаются в обоих режимах.
Положительные веса при обычном round-robin не влияют на частоту.
Продолжаем до `top_k` или исчерпания всех доступных списков; квот, оставляющих
выдачу незаполненной при наличии подходящих кандидатов, нет.

### Дедупликация: чанк и документ

`chunk_id` остаётся идентичностью результата. Разные чанки одного документа
могут содержать разные ответы, поэтому раннее схлопывание по `doc_id` не вводим.
Doc-level метрики продолжают брать лучший ранг документа; они не пополняют
выдачу до `top_k` уникальных документов. `top_k` остаётся числом чанков.

| Метод | Повторы внутри источника | Один чанк в разных источниках |
|---|---|---|
| RRF / weighted sum | Удаляются до расчёта | Вклады суммируются в один результат. |
| Interleave, `deduplicate: true` | Удаляются | Возвращается первое выбранное появление. |
| Interleave, `deduplicate: false` | Удаляются | Появления разных источников можно вернуть отдельно. |

Для RRF / weighted sum `deduplicate: false` становится ошибкой конфигурации
с подсказкой установить `true`: агрегация по чанку по определению объединяет
появления. Раньше `false` принимался, но ничего не менял. Это намеренное ужесточение
валидации; переход на `true` сохраняет прежний смысл такой настройки.
Для interleave `false` остаётся режимом абляции межисточниковых повторов.
Ограничение числа чанков на документ и дедупликация по похожему тексту — отдельные
политики разнообразия, которые стоит вводить после измерения проблемы.

## Настройки и совместимость

Ниже **предлагаемый фрагмент** сценария для гибридного поиска; новые поля пока
не принимаются текущей схемой. Настройки хранения и остальные секции опущены.

```yaml
retrieval:
  strategy: fanout_merge
  top_k: 30
  async: true
  sources:
    - name: vector
      kind: vector
      weight: 1.0
    - name: keyword
      kind: keyword
      weight: 1.0
  merge:
    method: weighted_sum
    normalize: minmax
    deduplicate: true
```

| Поле | Предложение |
|---|---|
| `retrieval.merge.normalize` | `minmax \| none`, default `minmax`; применяется только к weighted sum. |
| `retrieval.merge.interleave_weighted` | Boolean, default `false`; применяется только к interleave. |
| `retrieval.merge.rrf_k` | Целое `>= 1`, default 60; применяется только к RRF. |
| `retrieval.sources[].weight` | Конечное число `>= 0`; для fanout хотя бы один вес положителен. |
| `retrieval.merge.deduplicate` | Default `true`; `false` разрешён только для interleave в fanout. |

Неиспользуемые параметры с дефолтами остаются допустимыми: snapshot содержит
весь нормализованный блок. Для явно заданного недефолтного параметра другого
метода preflight выдаёт предупреждение с путём поля. Имена источников по-прежнему
уникальны; пустой fanout и все нулевые веса отклоняются до создания клиентов.
Вес 0 выключает **вклад в merge**, но источник всё ещё запрашивается и измеряется;
для исключения сетевого обращения источник нужно удалить из сценария.

`single` сохраняет текущий путь и raw scores, без fusion и без применения весов
или флага дедупликации. Валидация идентификаторов/конечных scores общая;
неиспользуемые недефолтные merge-настройки получают предупреждение.
Для тестирования merge с одной выдачей используется fanout с одним источником.
Глубина запроса к каждому источнику пока равна `retrieval.top_k`: новые бюджеты
кандидатов и дополнительные запросы для заполнения выдачи в эту задачу не входят.

Обычные конфиги с положительными весами и `deduplicate: true` загружаются как
раньше. Точные значения weighted-sum scores могут немного измениться из-за
убранного `+eps` в ненулевом знаменателе. Локальные дубли, равные итоговые scores
и взвешенный interleave получают явно определённое поведение. Старые результаты
не пересчитываем; сравнение версий учитывает commit и snapshot.

## Scores и потребители результата

В `RetrievedItem` добавляем `score_fused: float | None = None` в конце dataclass
и свойство `ranking_score`: fused, если он не `None`, иначе raw. Проверка именно
на `None`, поскольку 0 — корректный итоговый score.

- `score_raw` всегда остаётся score представителя, полученный от backend.
- RRF и weighted sum записывают математический результат в `score_fused`.
- Interleave записывает `1 / rank` итогового списка: это **порядковый score**,
  который отражает выбранное чередование, а не релевантность или вероятность.
- `single` оставляет `score_fused=None` и прежний `ranking_score=score_raw`.

[`context/engine.py`](../../src/ragglet/context/engine.py),
[`rerank/engine.py`](../../src/ragglet/rerank/engine.py) при отключённом rerank
и [`rerank/noop.py`](../../src/ragglet/rerank/noop.py) используют `ranking_score`.
Настоящий cross-encoder продолжает выдавать собственную оценку. Порядок retrieval
и doc-level проекция остаются источником рангов для метрик.

Для threshold/adaptive context после RRF и interleave меняется шкала; существующие
пороги нужно подобрать заново и проверить отдельным smoke. Единый threshold между
raw, RRF, weighted sum и порядковым score не обещается. Этот переход явно отмечаем
в документации и подсказке редактора; качество merge сначала измеряем без context.

При `output.include_debug_fields: true` добавляем в существующие строки per-query
`retrieved_scores_raw` и `retrieved_scores_fused`: списки в порядке `retrieved_ids`.
Для single fused-значения — `None` в Python. CSV использует существующий Python-repr
списков, Parquet сохраняет списки; API преобразует пропуски в JSON `null` без NaN.
В `registry/per_query.py` добавляем поля в `LIST_COLUMNS`: числовые scores и пропуски
должны сохранять тип после разбора, включая полностью пустую колонку.
Проверяем round trip и чтение старых результатов без новых колонок.
Эти поля показывают scores финального retrieval; для replay
полной выдачи источников нужен отдельный экспериментальный fixture.

Retrieval LRU хранит новые поля вместе с результатом. Сигнатура merge строится
из полного нормализованного блока настроек, чтобы новые параметры автоматически
влияли на ключ. Существующие веса и порядок источников остаются в sources signature.
Cache hit возвращает те же scores и debug-поля, но не создаёт новые замеры merge.

API получает настройки через существующую схему сценария и meta, без нового
маршрута. Редактор показывает normalization только для weighted sum, weighted
переключатель — для interleave; deduplicate доступен для переключения только там.
Обновляем registry полей, подсказки, переводы и schema fixtures. Таймер merge
по-прежнему охватывает преобразование, нормализацию, fusion, dedup и `top_k`.

## Проверка реализации

Новый `tests/test_merge.py` проверяет математические контракты на небольших
табличных примерах без внешних сервисов. Ожидаемые scores считаются независимо
от production helpers; одних snapshot-тестов списка недостаточно.

| Группа | Обязательные случаи |
|---|---|
| RRF | Пример выше; общий чанк двух источников; веса 2:1; локальный повтор не увеличивает вклад; изменение `rrf_k`; нулевой вес. |
| Weighted sum | Обе нормализации, разные шкалы, общий чанк, отрицательные scores, singleton, константный/пустой список, диапазон около epsilon; переполнение и нечисловые результаты отклоняются. |
| Interleave | Обычное чередование; последовательность 2:1; нулевой вес; короткий/пустой источник; пересечения; пополнение до `top_k` после пропуска дублей; `deduplicate: false`. |
| Идентичность | Разные point IDs одного чанка; разные чанки одного документа; конфликт `doc_id`/текста; пустые IDs; `top_k=1` и недостаток уникальных кандидатов. |
| Детерминизм | Равные scores; обратный порядок вставки ответов при сохранённом порядке источников; последовательный/async fanout; повторные вызовы; входные объекты не мутируются. |
| Конфиг | Defaults, неверный метод/нормализация, отрицательные/NaN/inf веса, все нули, `rrf_k<=0`, пустой fanout, правила `deduplicate: false`, предупреждения о неиспользуемых полях; preflight для cosine/dot и отказ weighted sum для Euclid/неизвестной метрики. |
| Потребители | Raw не перезаписан; fused=0 не превращается в raw; context, noop и настоящий rerank; каждый новый параметр меняет cache key; cache hit эквивалентен miss. |
| Интеграция | Фейковые vector/BM25 источники через `retrieve_items`, single и fanout с одной выдачей; CSV/Parquet/API, старые артефакты, UI round trip и ошибки по пути поля. |

Сохраняем регрессионные проверки retrieval timing, отмены и таймаутов: обновление
merge не должно менять политику ошибок fanout. Обязательны backend/frontend
проверки проекта и существующий сквозной API-тест; реальные прогоны ниже дополняют
тесты, а не заменяются ими.

## Экспериментальное сравнение

Сравнение имеет два слоя. **Replay** подаёт всем методам одни и те же сохранённые
кандидаты, изолируя merge от приближённого поиска. **Полный retrieval** проверяет,
сохраняется ли эффект на single, гибридной выдаче и двух однородных шардах.

Добавляем `scripts/evaluate_merge.py`: режим захвата кандидатов использует
существующие адаптеры и конфигурацию сценария, сохраняет для каждого qid порядок
источников и список `(chunk_id, doc_id, score_raw)`; режим replay читает этот fixture,
параметры merge и qrels, вызывает production merge/evaluation и пишет scores,
ранжирования и метрики. Захват не должен сохранять тексты, payload или адреса
backend. До удаления текстов захват проверяет конфликты идентичности чанков;
так replay не скрывает некорректный payload. Метрика и направление score источника
сохраняются, чтобы replay также проверял применимость weighted sum.
Это локальный экспериментальный формат с явной версией, не новый API.
Синтетические fixtures коммитятся вместе со скриптом; данные реального benchmark
публикуются только при допустимой лицензии и после проверки содержимого.

| Сценарий | Сравнения |
|---|---|
| Одиночный | Неизменённый single; fanout с одной и той же выдачей для каждого merge. Порядок при положительном весе должен совпадать с входным для монотонных scores, включая константные списки. |
| Гибридный | Vector + BM25 одного корпуса: RRF, weighted sum/minmax, interleave обычный и взвешенный. `none` — контроль несопоставимых шкал. |
| Непересекающиеся шарды | Single на полном корпусе и fanout на его разбиении: RRF, weighted sum/minmax, weighted sum/none, оба interleave. Одни и те же embedding и метрика. |
| Перекрытия | Реплики и частично общие чанки, локальные дубли, несколько чанков документа: влияние голосов источников и межисточниковой дедупликации. |

Порядок эксперимента:

1. Малый синтетический corpus с полными точными выдачами: для непересекающихся
   шардов, равных весов и `none` слияние обязано совпасть с глобальным score-sort.
   Это проверка корректности; она не обещает равенства с single ANN-поиском.
2. Публичный датасет с qrels, например уже поддержанный NFCorpus. Фиксируем
   revision, хэши corpus/queries/qrels, chunking, модель и её revision, параметры
   поиска, `top_k=30`, seed и набор qid. Demo служит только smoke.
3. Захватываем кандидатов один раз на каждую топологию, затем replay: RRF с
   `rrf_k` из `{10, 60, 100}`, weighted sum с обеими нормализациями, оба interleave.
   Для гибридного поиска проверяем отношения весов `{1:1, 2:1, 1:2}`.
   На однородных шардах основной вариант — равные веса; неравные — абляция.
4. До подбора выделяем непересекающиеся tuning/evaluation qid с seed 42 и
   сохраняем их списки. Если есть официальный validation split, используем его;
   иначе явно описываем собственное разбиение. Веса и параметры выбираются только
   по tuning; итоговый отчёт показывает результат на отложенных запросах.
5. Запускаем выбранные варианты end-to-end с выключенными cache, rerank, context
   и generation; одинаковые concurrency, query order и достаточные бюджеты.
   Пять повторов, порядок вариантов чередуется. Async/sequence дополнительно
   сверяются по выдаче; прогрев не включается в замеры.
6. Проверяем один отдельный прогон с настоящим rerank и один с context, затем
   cache hit/miss. Так эффект fusion не смешивается с другими стадиями, но
   интеграционная совместимость тоже проверяется.

Основная метрика — `doc_ndcg@10`; дополнительные — `doc_recall@10`, `doc_mrr@10`,
`doc_hit@10`, результаты при k=1/3/5, `n_docs`, `n_chunks`, `dup_chunks`.
Для производительности — `lat_merge` и `lat_retrieve` p50/p95/p99, throughput,
timeout rate и число завершённых запросов. Перцентили повторов не объединяем
усреднением в «общий p95»; при необходимости пересчитываем по исходным строкам.

Отчёт включает парные разности по qid и 95% bootstrap-интервал (10 000 выборок,
seed 42); единица выборки — запрос, а не повтор. Для повторяющихся измерений
сначала усредняем метрику одного qid по повторам. Timeout учитывается по текущему
правилу нулевого качества и отдельно показывается, чтобы не принять сетевой
эффект за улучшение merge.

Формат итоговой таблицы: сценарий, метод, normalization, веса, `rrf_k`, число qid,
изменение nDCG/recall относительно baseline с интервалом, merge p95, retrieve p95,
timeout rate. При replay сравниваем старое поведение на `4793017` и реализацию
на одинаковом fixture; адаптер legacy-кода живёт в экспериментальном скрипте,
а не становится ещё одним production-режимом. В отчёте указываем оба commit.

Результат приёмки — воспроизводимый отчёт с заполненными числами, объяснением
выигрышей/потерь и рекомендацией по каждой топологии. Улучшение S5 заранее не
заявляется. Вариант рекомендуем как улучшение качества, если нижняя граница
интервала ΔnDCG@10 положительна, а средний recall@10 не падает более чем на 0,01
в абсолютных единицах; latency приводим рядом как стоимость выбора. При отсутствии
такого результата сохраняем baseline и фиксируем, что гипотеза не подтвердилась.
Общий default RRF меняется только отдельным обоснованным решением.

## Этапы реализации

После обсуждения дизайна изменения добавляются в эту же ветку и PR:

1. Контракт merge и конфигурация: подготовка кандидатов, детерминизм, нормализация,
   weighted interleave, валидация и табличные unit-тесты.
2. Интеграция: raw/fused scores и потребители, cache signatures, debug-колонки,
   API/meta, редактор и регрессия timing/артефактов.
3. Экспериментальный скрипт и fixtures, конфиги сравнений, измерения и отчёт;
   обновление README, config reference, metrics и описания архитектуры.

Реализация не требует новых сервисов или миграции существующих прогонов.
Частичные ответы при отказе, новые таймауты, настоящая кластеризация, learned
fusion и автоматическое определение реплик остаются за границами этой задачи.
Сложность RRF/weighted sum — O(N + U log U), где N — число входных кандидатов,
U — уникальных чанков; weighted interleave — O(N + top_k × S) для S источников.
Память — O(N). При текущих коротких выдачах сначала измеряем эти реализации,
прежде чем добавлять оптимизации.
