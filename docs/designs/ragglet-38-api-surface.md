# ragglet-38 — Единый API-контур: рамка

**Коротко.** Всё, что трогает стенд (прогон, его проверка, сборка индекса), идёт через
один вход — REST API. CLI, веб-интерфейс и curl становятся его клиентами. Стенд — это
машина с Qdrant, Redis и моделями, на которой идут замеры. Под API лежит ядро: обычная
Python-библиотека, у операций которой одна форма. Этот документ — рамка для задач этапа 3
(28, 29, 30, 37) и веб-интерфейса (15, 31): конкретные endpoints, очередь и реестр
проектируются в них, а здесь закреплены правила, на которые они опираются. В этом же PR
ядро приводится к этой форме: API ещё нет, но 28 и 29 строятся уже на готовом коде.

## Пример, на котором всё объясняется

Исследователь собирает индекс nfcorpus в коллекцию `nfcorpus_v1` и прогоняет на ней
сценарий `nfcorpus_hf`. Через месяц то же самое захочется делать из веб-интерфейса.

**Сейчас** обе операции запускаются из терминала: `ragglet index build` и
`ragglet bench run`. CLI вызывает функции ядра напрямую.

**Если просто добавить UI рядом** (UI → API → ядро, а CLI по-прежнему → ядро), у стенда
появляются два независимых входа. В UI идёт прогон на `nfcorpus_v1`, а в терминале
запускают `index build` с тем же профилем. Сборка первым делом пересоздаёт коллекцию, и
прогон начинает получать пустую выдачу. Даже если коллекции разные, два тяжёлых процесса
делят CPU, и задержки в прогоне уже не про RAG. Ни один вход не знает о другом: UI не
видит прогон из терминала и не может его отменить.

**После рамки** вход один:

| Кто | Действие | Что происходит |
|---|---|---|
| UI | кнопка «Запустить» | запрос в API |
| CLI | `ragglet bench run s.yaml` | тот же запрос в API |
| скрипт | `curl -X POST …` | тот же запрос в API |

API отдаёт задачу менеджеру задач. Менеджер видит, что на стенде уже идёт прогон, и
ставит сборку в очередь. Обе задачи видны в UI, обе можно отменить, обе попадают в реестр.

## Решения

### 1. Один вход

Прогон, dry-run (проверка без запуска) и сборка индекса идут только через API. Доступ к
прошлым прогонам (детали, сравнение) тоже через API, хотя стенд он не трогает.

### 2. Ядро — библиотека, операции одной формы

```
операция(конфиг, *, dry_run=False, progress=...) -> результат
```

- **`dry_run=True`** — только проверки, без побочных эффектов: не создаётся каталог
  прогона, не пересоздаётся коллекция, не загружаются модели.
- **`progress(stage, done, total)`** — ядро сообщает ход работы: `queries` у прогона
  (по всем повторам), `corpus` у сборки. CLI рисует полосу, менеджер задач будет хранить
  это как статус для UI.
- **Результат** — dataclass, а не dict, чтобы из него напрямую получалась схема ответа API.
- **Ошибки.** Неверный конфиг, датасет или индекс — `ValidationError` со списком `Issue`,
  и только до побочных эффектов. В CLI это код выхода 2, в API — ответ 422 с тем же
  списком. Любое другое исключение — сбой задачи, трейсбек уходит в её лог.

Операций сейчас две: `run_scenario` и `build_index`. `compare_runs` только читает
артефакты и операцией не считается. Новая операция — это функция ядра такой формы, тип
задачи в 29 и endpoint в 28. Отдельные команды и validate-ручки в обход этой схемы не
заводятся.

Ядро вызывают воркер менеджера задач и тесты, им же можно отлаживаться без сервера.

### 3. Менеджер задач (ragglet-29)

- Прогон и сборка индекса — два типа задач.
- На стенде одна тяжёлая задача за раз, остальные ждут в очереди.
- Каждая задача выполняется в свежем процессе: прогретые модели и кэши не переходят из
  прогона в прогон (это важно для ragglet-20), а падение задачи не роняет сервер.
- Статус, прогресс, отмена, лог.

### 4. Контракт API (ragglet-28)

- Версия в пути: `/v1/…`.
- Конфиг передаётся содержимым, а не путём: сервер может работать в контейнере и не
  видеть файлов клиента.
- Долгая операция сразу отвечает 202 и id задачи, дальше статус запрашивается отдельно.
- Конкретные endpoints и схемы решаются в 28, после требований дизайна UI (ragglet-15).

### 5. Реестр (ragglet-30)

В реестр попадают все прогоны и сборки, с какого бы клиента их ни запустили: путь у них
один.

### 6. CLI — переход одним шагом (ragglet-37)

Пока 28 и 29 не готовы, CLI вызывает ядро напрямую, как сейчас. Когда они готовы, CLI
становится клиентом на typer + httpx, без режима «локально». Сервер поднимается через
`ragglet serve` или docker compose. Если он не запущен, CLI так и говорит, а не вызывает
ядро сам. На bash+curl CLI не пишется: опрос статуса, отмену и коды выхода там не
протестировать.

## Что делается в этом PR

Подготовка ядра, без API:

- `run_scenario(cfg, *, dry_run, progress) -> RunResult`. `validate_scenario` удаляется:
  dry-run — это тот же путь, остановленный после preflight.
- `build_index(cfg, *, dry_run, progress) -> BuildResult`. Dry-run проверяет датасет и
  storage и возвращает, какие коллекции будут пересозданы, не загружая модель и не
  подключаясь к Qdrant. `rich.track` уходит из ядра в CLI.
- Схема конфига разрешает `pgvector`, `milvus` и `weaviate`, но реализован только
  `qdrant`. Проверка была скопирована в три места и бросала `NotImplementedError`; теперь
  она одна и даёт `ValidationError` с кодом `storage.not_implemented`.
- Если коллекции нет (индекс ещё не собирали), preflight даёт ошибку
  `index.no_collection` с подсказкой пересобрать индекс. Раньше `bench run` падал с
  трейсбеком клиента Qdrant, а `bench validate` печатал его текст одной строкой.
- CLI: `bench validate` заменяется на `bench run --dry-run`, появляется
  `index build --dry-run`. Ошибки обрабатываются одинаково: `ValidationError` → код 2,
  остальное — трейсбек. У `bench run` появляется полоса прогресса. Мёртвый `cli/cli.py`
  и заглушка `serve` удаляются.

## Что меняется для пользователя

- Команды `ragglet bench validate X` больше нет. `ragglet bench run X --dry-run` печатает
  тот же отчёт. Переходного алиаса нет, README и команды в
  `docs/article-experiments-audit.md` обновлены.
- `bench validate` выходил с кодом 1 на несовместимый индекс, а прочие ошибки (например,
  недоступный Qdrant) печатал одной строкой с кодом 2. Теперь всё как у `bench run`:
  код 2 со списком проблем, остальное — трейсбек.

Не меняются формат артефактов, `manifest.json`, метаданные индекса (пересобирать индексы
не нужно), `compare_runs`, сценарии и профили.

Прогресс сообщается после того, как запрос записал свои задержки, поэтому в `lat_*` он
не попадает. Полоса в CLI рисуется без фонового потока (он отнимал бы GIL у замеров) и
перерисовывается не чаще раза в секунду, между запросами.

ragglet-19 (PR #7, пока план) тоже меняет `bench/query_loop.py`. Здесь это одна строка
в `_Launcher`, конфликт тривиальный.

## Как на рамку опираются другие задачи

| Задача | Что берёт из рамки |
|---|---|
| ragglet-28, REST API | единственный вход, включая сборку индекса; конфиг содержимым; 422 со списком `Issue`; 202 и id задачи |
| ragglet-29, менеджер задач | два типа задач, одна тяжёлая на стенд, свежий процесс, `progress` из ядра, отмена |
| ragglet-30, реестр | все прогоны и сборки от любого клиента |
| ragglet-15 и 31, UI | только через API; CLI работает через тот же API, а не «самостоятельно»; страница индексов — по желанию |
| ragglet-34, Docker | API-сервер в compose: без него не работает CLI |
| ragglet-37, CLI | клиент на typer + httpx одним шагом после 28 и 29 |

## Не входит

- endpoints и схемы запросов и ответов — 28;
- очередь, процессы, отмена — 29;
- id прогонов и хранение — 30;
- остальные `NotImplementedError` на неверные значения конфига (стратегия retrieval,
  провайдер rerank и т.п.). Через API они пока будут сбоем задачи, а не 422. Перевести их
  в `ValidationError` стоит в 28, если понадобится.

## Тесты

1. Dry-run прогона возвращает результат preflight, не создаёт каталог прогона и не
   загружает модель.
2. Dry-run сборки не трогает коллекции и не загружает модель, а на битом датасете бросает
   `ValidationError`.
3. Прогресс: прогон из двух повторов по 3 запроса сообщает `done` от 1 до 6 при
   `total` 6. Сборка сообщает по документам до `total`.
4. Неподдерживаемый backend даёт `ValidationError` `storage.not_implemented` и в прогоне,
   и в сборке. Отсутствующая коллекция даёт одну ошибку `index.no_collection`, без
   `index.no_metadata` поверх.
5. CLI через `CliRunner`: `bench run --dry-run` печатает отчёт и выходит с кодом 0;
   `ValidationError` даёт код 2 и список проблем; `index build --dry-run` печатает
   коллекции, которые будут пересозданы.
6. Существующие тесты переходят на `RunResult` и `BuildResult`.
