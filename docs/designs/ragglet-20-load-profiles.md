# ragglet-20 — Профили нагрузки и прогрев

**Коротко.** Сейчас замер начинается сразу после загрузки моделей. Кэши при этом в том
состоянии, в каком их оставил предыдущий повтор или даже вчерашний прогон. Задача вводит
фиксированный порядок: загрузка, потом прогрев системы, потом измерения. Каждое
измерение начинается с объявленного состояния кэша: холодного (пустого) или тёплого
(заполненного запросами этого измерения). В одном прогоне можно задать несколько
измерений — **фаз**: например, холодную и тёплую или четыре уровня конкурентности. У
каждой фазы своя статистика. Отдельно записываются правила seed и переиспользования
моделей. Блок `run` с прогревом, фазами и повторами — это и есть **профиль нагрузки**.

## Ценность и объём в двух словах

Половина формулировки задачи уже сделана: повторы есть (`run.repeats`), уровень
конкурентности есть (ragglet-18), seed есть. Остаются три настоящие проблемы.

1. **Кэш смешивает холодные и тёплые запросы.** Кэш retrieval переживает повторы: повтор 0
   холодный, остальные тёплые, а агрегат их усредняет. На ноде агента это даёт p50 16,9 ±
   10,5 мс, хотя на деле холодный повтор — 28,9 мс, а тёплый — 10,8. Чем больше повторов,
   тем лучше выглядит кэш. Это прямо нарушает критерий приёмки задачи.
2. **Холодное состояние не воспроизводится.** Кэш эмбеддингов в Redis общий для всех
   прогонов и живёт сутки. «Холодный» прогон может оказаться тёплым после вчерашнего. Для
   статьи Redis чистили руками, и четыре прогона пришлось выбросить: почистили не тот
   Redis.
3. **Кривая latency–throughput требует N отдельных прогонов.** Каждый заново грузит
   модели, у каждого свой холодный старт, уровни меряются в разное время, и общей таблицы
   нет.

Сам прогрев системы (первый вызов модели, соединения) на ноде даёт мало: один медленный
запрос в начале процесса, p50 он не двигает. Но с фазами этот запрос всегда достаётся
одной и той же фазе — первой в повторе 0. На Mac с MPS, с настоящим Qdrant и с удалённой
LLM эффект, скорее всего, больше. Это дешёвая страховка, а не главная ценность.

**Объём** средний, примерно как у ragglet-18: около 200 строк кода, 12 тестов,
документация, один PR из четырёх коммитов. Самая дорогая часть — фазы, то есть несколько
измерений в одном прогоне: они меняют раскладку артефактов. Фазы решено делать. Открытая
модель нагрузки занимает ещё около 30 строк, её можно вынести в отдельную задачу.
Открытые вопросы — в разделе «Вопросы на решение».

## Пример, на котором всё объясняется

Сценарий nfcorpus (323 запроса): векторный поиск, `concurrency: 1`, три повтора,
`shuffle: false`. Включён кэш retrieval в памяти (LRU). Это замер на ноде агента, детали в
приложении.

**Сейчас** summary по повторам такой:

| повтор | что в кэше на старте | `lat_total_p50`, мс | `throughput_qps` | `ret_hit_rate` |
|---|---|---|---|---|
| 0 | ничего | 28,9 | 26,1 | 0 |
| 1 | все 323 запроса | 10,8 | 81,4 | 1 |
| 2 | все 323 запроса | 10,8 | 90,0 | 1 |
| **агрегат** | | **16,9 ± 10,5** | **65,8 ± 34,7** | **0,67** |

Агрегат не описывает ни холодную систему, ни тёплую. Он отвечает на вопрос «какая
задержка, если кэш тёплый в двух случаях из трёх». Доля тёплых при этом зависит от
`repeats`: при пяти повторах p50 был бы около 14,4, при десяти — 12,6. Настройка, которая
должна только уменьшать шум, меняет результат. Разброс ± 10,5 — тоже не шум: тот же
сценарий без кэша даёт 30,0 ± 0,3.

**После этой задачи** тот же эксперимент записывается так:

```yaml
run:
  repeats: 3
  shuffle: false
  phases:
    - name: cold
      cache: cold
    - name: warm
      cache: warm
```

В `summary.aggregate` будет по строке на фазу:

| фаза | `lat_total_p50`, мс | `throughput_qps` | `ret_hit_rate` |
|---|---|---|---|
| cold | ≈ 30 ± 0,3 | ≈ 27 ± 0,7 | 0 |
| warm | ≈ 10,8 ± 0,1 | ≈ 86 ± 6 | 1 |

Значения ожидаемые: холодная фаза взята из замера без кэша, тёплая — из повторов 1–2.
Каждый повтор каждой фазы начинается из одного и того же состояния. Поэтому разброс снова
показывает шум, а эффект кэша — это разница между строками: p50 почти втрое ниже.

Кривая из ragglet-19 записывается так же: фазы `c1`, `c2`, `c4`, `c8` с разным `load` в
одном прогоне вместо четырёх прогонов.

## Термины

- **Фаза** — одно измерение внутри прогона: модель нагрузки и состояние кэша на старте. У
  фазы свои строки `per_query` и свой summary. В прогоне одна фаза или несколько.
- **Повтор** — один проход фазы по всем запросам датасета. После задачи все повторы фазы
  стартуют из одного состояния и отличаются только шумом.
- **Прогрев системы** — несколько запросов перед измерениями. Их результаты в статистику
  не входят. Прогрев нужен, чтобы разовые расходы процесса не попали в замер: первый вызов
  модели, запуск рабочих потоков, открытие соединений с Qdrant и LLM.
- **Тепло системы и тепло кэша.** Это разные вещи, и задача держит их порознь.
  - Тепло системы: модели загружены и уже вызывались, соединения открыты, данные Qdrant
    лежат в памяти ОС. Это артефакт запуска бенчмарка, а не свойство архитектуры. Во всех
    фазах оно одинаковое: прогрев набирает его один раз.
  - Тепло кэша: в кэше эмбеддингов и в кэше retrieval уже лежат ответы на запросы. Это и
    есть исследуемая оптимизация (S4). Его состояние задаётся явно в каждой фазе.
- **Холодный кэш** (`cold`): кэши пусты. **Тёплый кэш** (`warm`): в кэшах лежат все
  запросы фазы.
- **Профиль нагрузки** — блок `run`: прогрев, фазы, повторы, порядок запросов. Вместе с
  `seed` он полностью определяет, какие запросы выполнятся, в каком порядке, когда и при
  каком состоянии кэша.

## Решение

### 1. Профиль нагрузки в сценарии

```yaml
run:
  repeats: 3
  shuffle: true
  warmup:
    queries: 16
  phases:
    - name: c1
      load: {type: closed, concurrency: 1}
    - name: c4
      load: {type: closed, concurrency: 4}
```

- `warmup.queries` — сколько запросов идёт в прогрев; 0 выключает прогрев.
- `phases` — список фаз. У фазы три поля:
  - `name` — уникальное имя из букв, цифр, `_` и `-`, оно попадает в имя файла;
  - `load` — модель нагрузки, как `run.load` из ragglet-18;
  - `cache` — `cold` или `warm`, по умолчанию `cold`.
- По умолчанию одна фаза `{name: main, load: {type: closed, concurrency: 1}, cache: cold}`.

`run.load` переезжает внутрь фазы. Это срез без совместимости: ни один сценарий в
репозитории `run.load` не задаёт, поэтому правятся только документация и тесты.
`cache: warm` при выключенном кэше — ошибка конфига: прогревать нечего.

### 2. Порядок подготовки и измерений

Порядок фиксирован и одинаков для любого сценария:

1. preflight, загрузка моделей, подключения — как сейчас;
2. прогрев системы (п. 3);
3. для каждого повтора r и для каждой фазы по порядку:
   - кэш приводится к состоянию фазы (п. 4);
   - запросы выполняются в порядке повтора r с моделью нагрузки фазы, строки пишутся в
     `per_query.<фаза>.repeat<r>`;
4. итоги: summary на каждую пару (фаза, повтор) и агрегат по повторам отдельно для каждой
   фазы.

Фазы **чередуются** внутри повтора: c1, c4, c1, c4 и так далее, а не сначала все повторы
c1, потом все c4. За время прогона стенд может медленно меняться: ноутбук греется и
сбрасывает частоту, Qdrant сливает сегменты, в фоне что-то запустилось. При чередовании
такой дрейф поровну задевает все фазы, а не ложится на последнюю. Это ничего не стоит:
каждая фаза и так начинается с подготовки кэша.

### 3. Прогрев системы

**Зачем.** Первые запросы свежего процесса идут медленнее остальных, и причины к
архитектуре RAG отношения не имеют:
- модель вызывается впервые (на Mac с MPS при этом ещё и компилируются шейдеры);
- соединения с Qdrant и LLM ещё не открыты;
- рабочие потоки не запущены;
- данные Qdrant после рестарта ещё не в памяти.

Эти разовые расходы ложатся на первые запросы повтора 0. Прогрев — это несколько запросов
до начала замера, результаты которых выбрасываются. Замер начинается на системе, которая
уже разогналась.

С фазами это важнее, чем без них: холодный старт всегда достаётся первой фазе повтора 0. В
примере выше первая фаза — `cold`. Без прогрева к ней добавится ещё и холодный старт
процесса, и эффект кэша окажется завышен. В свипе c1/c2/c4/c8 по той же причине
пострадает c1. Ошибка небольшая, но всегда в одну сторону и всегда на одной фазе.

**Насколько это много.** На ноде агента (CPU) холодный старт — один медленный запрос в
начале процесса: 78–118 мс при медиане 30, в трёх свежих процессах из четырёх. Это уровень
обычного хвоста: на nfcorpus он не двигает p50 и почти не двигает p99. На MPS, с настоящим
Qdrant и с удалённой LLM (у неё первое соединение — это TLS) эффект, скорее всего, больше.
Насколько, покажет `per_query.warmup` в smoke на Mac.

**Как устроен.** Перед первым измерением выполняется `warmup.queries` запросов датасета,
по одному, через весь конвейер, включая реранк и генерацию. Запросы выбираются из датасета по seed (п. 6).
Если прогрев длиннее датасета, список идёт по кругу. Строки прогрева пишутся в
`per_query.warmup`, в summary они не входят. По ним видно, насколько велик холодный старт
на конкретном стенде.

Прогрев набирает только тепло системы. Кэши после него каждая фаза приводит к своему
состоянию (п. 4), поэтому холодная фаза холодной и останется.

Прогрев задаётся числом запросов, а не временем, потому что число одинаково на любом
железе и прогон воспроизводится. Прогрев идёт один раз, а не перед каждой фазой, потому
что после него тепло системы уже набрано. Переходный режим в начале каждой фазы — другой
эффект, см. «Ограничения».

### 4. Состояние кэша: cold и warm

| состояние | кэш эмбеддингов (Redis) | кэш retrieval (LRU) | модели, соединения, Qdrant |
|---|---|---|---|
| `cold` | пуст | пуст | прогреты |
| `warm` | все запросы фазы | все запросы фазы | прогреты |

Перед каждым повтором каждой фазы:

- `cold` — оба кэша очищаются;
- `warm` — оба кэша очищаются, потом для каждого запроса фазы считаются и кладутся в кэш
  эмбеддинг и выдача поиска. Этот проход идёт только по кэшируемым этапам: реранк и
  генерация не вызываются, поэтому тёплая фаза не тратит деньги на LLM.

Чтобы очистка была безопасной и полной, у прогона **своё пространство ключей в Redis**: к
нынешнему префиксу `emb:<модель>@<ревизия>:<normalize>` добавляется id прогона. Очистка
удаляет только ключи своего прогона, и в конце прогона они тоже удаляются. Чужие ключи и
другие базы Redis не трогаются никогда. Если процесс упал, остаток истечёт по TTL. Ручная
чистка из аудита статьи больше не нужна, и почистить не тот Redis уже нельзя.

Цена решения: кэш эмбеддингов больше не переживает прогоны. Тёплое состояние между
процессами сейчас никто специально не меряет, а тёплая фаза даёт то же самое внутри
прогона.

Очистка не трогает три вещи: память ОС с данными Qdrant, внутренние кэши Qdrant и кэш
промптов у провайдера LLM. Первые две — тепло системы, его набирает прогрев. Третью
контролировать нельзя, см. «Ограничения».

Побочный эффект. Если кэш вмещает все запросы фазы, каждый запрос в ней либо промах
(`cold`), либо попадание (`warm`). Тогда `emb_hit_rate` и `ret_hit_rate` в summary точны
при любой конкурентности: ровно 0 или 1. Правильный подсчёт для смешанных нагрузок
по-прежнему за ragglet-22.

### 5. Несколько фаз в одном прогоне

Чем фазы лучше N отдельных прогонов:

- модели грузятся и прогреваются один раз, все фазы меряются на одном и том же тепле
  системы;
- фазы чередуются (п. 2), поэтому медленный дрейф стенда не путается с разницей между
  фазами;
- внутри повтора все фазы идут в одном порядке запросов, поэтому сравнение парное;
- результат — один каталог и одна таблица `summary.aggregate`, где строка — фаза. Для
  кривой latency–throughput это готовые точки.

Это ровно две строки, которые таблица ragglet-18 отложила сюда: «несколько уровней
конкурентности с отдельной статистикой на каждый» и «холодная и тёплая фазы».

Одна задача (job) в API ragglet-38 по-прежнему соответствует одному прогону. Свип по
конкурентности занимает стенд одной задачей с одним прогревом, а не четырьмя.

### 6. Seed и переиспользование моделей

**Seed.** У каждой случайности в прогоне свой поток. Он выводится из `seed` сценария,
назначения и номера повтора: `Random(f"{seed}/{назначение}/{r}")`.

| назначение | что решает | от чего зависит |
|---|---|---|
| `order` | порядок запросов в повторе r при `shuffle: true` | seed, r |
| `load` | случайность модели нагрузки в повторе r | seed, r |
| `warmup` | какие запросы идут в прогрев | seed |

Отсюда три следствия:

- в повторе r все фазы получают один и тот же порядок и одно расписание запусков, то есть
  фазы отличаются только тем, что в них объявлено;
- разные повторы получают разные порядки и расписания, то есть повторы остаются
  независимыми выборками;
- если добавить фазу или прогрев, порядок запросов в остальных фазах не сдвинется.

Сейчас порядок повтора r задаёт r-е число из `Random(seed)`. Новое правило один раз
поменяет порядок запросов в прогонах с `shuffle: true`. Набор запросов и качество
останутся прежними.

**Модели и соединения.** Модели, их полосы (ragglet-18) и клиенты Qdrant, Redis и LLM
создаются один раз на прогон. Они общие для прогрева, всех фаз и всех повторов. Между
фазами и повторами ничего не перезагружается. Холодный старт процесса как метрика продукта
(например, для serverless) — это другой эксперимент, см. «Вне скоупа».

### 7. Итоги и артефакты

- `per_query.<фаза>.repeat<r>.{csv,parquet}` — строки фазы, колонки как в ragglet-19.
- `per_query.warmup.{csv,parquet}` — строки прогрева.
- `summary.{json,csv}` — строка на пару (фаза, повтор), новая колонка `phase`.
- `summary.aggregate.{json,csv}` — строка на фазу: среднее, std, min и max по повторам,
  правила ragglet-19 не меняются. JSON становится списком, как `summary.json`.
- `RunResult.summary` содержит агрегаты по фазам.

Внутри фазы итоги считаются ровно по правилам ragglet-19, `summarize_repeat` не меняется.
`compare_runs` тоже не меняется: фазы и прогрев лежат в snapshot как `scenario.run.*`, и
различие в них — различие класса config.

### 8. Открытая модель нагрузки (можно вынести)

**Зачем.** Модель нагрузки решает, когда запускать очередной запрос. Сейчас есть только
закрытая: N пользователей, и каждый шлёт следующий запрос, только получив ответ на
предыдущий. Если система тормозит, пользователи тоже начинают слать реже, то есть нагрузка
подстраивается под систему. Открытая модель задаёт поток, например «20 запросов в
секунду», и не смотрит, успевает ли система. Так приходит трафик в реальный сервис:
пользователи не знают друг о друге и не ждут чужих ответов.

Разница видна, когда система не справляется. Пример: запрос обрабатывается 40 мс, по
одному за раз, то есть система выдерживает 25 запросов в секунду.

| нагрузка | что происходит | задержка |
|---|---|---|
| закрытая, 4 пользователя | каждый ждёт, пока обработают трёх других, и только потом шлёт снова; поток сам падает до 25 в секунду | ~160 мс, сколько ни меряй |
| открытая, 30 в секунду | каждую секунду приходит 30 запросов, обрабатывается 25, очередь растёт на 5 в секунду | через 10 с около 2 с ожидания, дальше таймауты |

Закрытая модель отвечает на вопрос «как работает система с N одновременными
пользователями». Открытая отвечает на вопрос «выдержит ли она X запросов в секунду и какая
при этом будет задержка». Второй вопрос — про ёмкость сервиса: сколько трафика держит
конфигурация при p95 не выше заданного. Свип закрытой модели по `concurrency` тоже даёт
кривую latency–throughput, но возле насыщения он занижает задержку: пользователи сами
притормаживают.

**Как устроена.** Это новая запись в реестре `LOAD_MODELS`, ядро не меняется:

```yaml
load:
  type: open
  rate_qps: 20
  arrivals: poisson    # или constant
```

Запросы приходят 20 раз в секунду, ровно или со случайными интервалами. Всё нужное для
этого уже есть в ядре ragglet-18: плановый момент запуска, а от него часы
запроса и бюджет. Если запуски не успевают за расписанием, опоздание попадает в задержку,
а не теряется. Число запросов в работе ограничено бюджетом: не больше `rate_qps ×
total_ms`. Случайные интервалы берутся из потока `load` (п. 6).

**Нужна ли сейчас.** От неё ничего в задаче не зависит, и ядро ragglet-18 её уже
допускает: добавить можно в любой момент одной записью в реестре. Если вопрос «сколько
запросов в секунду выдержит конфигурация» для экспериментов сейчас не стоит, модель лучше
вынести в отдельную задачу.

## Вопросы на решение

1. **Включать ли прогрев по умолчанию.** Рекомендую включить с `warmup.queries: 16`.
   Гарантия «замер начинается на прогретой системе» должна быть у каждого прогона, а
   стоит она меньше секунды. Без прогрева холодный старт всегда ложится на первую фазу
   повтора 0 (п. 3). В сценариях с платной генерацией прогрев — это 16 вызовов LLM на
   прогон. Альтернатива — 0 по умолчанию, прогрев только по явной настройке.
2. **Делать ли открытую модель здесь.** Она небольшая и не зависит от остального (п. 8).
   Если вопрос «сколько запросов в секунду выдержит конфигурация» сейчас не стоит,
   рекомендую вынести её в отдельную задачу. Если стоит — делать здесь, отдельным
   коммитом.

## Ограничения

- **Переходный режим в начале и в конце фазы.** При `concurrency: 4` первые запросы фазы
  идут, пока очередь к модели ещё не набралась: на ноде это 34, 52 и 82 мс при устойчивых
  ~113. В конце фазы воркеры освобождаются по одному. Искажение пропускной способности —
  примерно concurrency / (2n), на nfcorpus около 1% при c=8 (ragglet-19). Обрезать края
  значит менять набор запросов, по которому считается качество, поэтому не обрезаем.
- **Кэш промптов у провайдера LLM.** OpenAI и другие провайдеры кэшируют одинаковые длинные
  промпты на своей стороне. Начиная со второго прохода, генерация может стать быстрее и
  дешевле, и сбросить это из ragglet нельзя. Чередование делит эффект поровну между фазами,
  кроме первой фазы повтора 0.
- **Кэш меньше фазы.** Если `cache.retrieval.size` меньше числа запросов, часть записей
  вытеснится ещё при подготовке, и тёплая фаза будет состоять не только из попаданий. Это
  честный эффект, его разбор — ragglet-22.

## Тесты (критерий приёмки)

На фейках, без Qdrant и torch, как в ragglet-18 и ragglet-19.

1. Фазы `cold` и `warm` с LRU-кэшем, три повтора: в каждом повторе холодной фазы все
   запросы — промахи, тёплой — попадания, качество одинаковое. Сейчас по повторам было бы
   0, 1, 1.
2. Очистка Redis удаляет только ключи своего прогона. Чужой ключ с тем же префиксом модели
   остаётся, свои ключи после прогона удалены. Redis здесь — заглушка клиента.
3. Подготовка тёплой фазы не вызывает реранкер и генератор.
4. Прогрев: до первого измерения выполнено `warmup.queries` запросов, в summary их нет, в
   `per_query.warmup` их ровно столько же. При том же seed это те же запросы. Если прогрев
   длиннее датасета, запросы идут по кругу.
5. При двух фазах и двух повторах порядок выполнения такой: r0 A, r0 B, r1 A, r1 B.
6. Внутри повтора у всех фаз один порядок запросов. Добавление фазы или прогрева порядок
   не меняет. У разных повторов порядки разные.
7. Модель нагрузки получает разный seed в разных повторах и одинаковый в фазах одного
   повтора.
8. Конфиг: повторное имя фазы, недопустимое имя, имя `warmup`, `cache: warm` без кэша и
   старый `run.load` дают понятную ошибку.
9. Артефакты: `per_query.<фаза>.repeat<r>`, `summary` с колонкой `phase`, в агрегате
   строка на фазу.
10. Модель `open` с `constant` даёт плановые моменты i / rate_qps. С `poisson` расписание
    воспроизводится по seed. При медленном фейковом store задержка включает ожидание от
    планового момента.
11. В прогоне с фазами и повторами модели загружаются один раз (счётчик в фейке).
12. Существующие тесты проходят.

E2E на ноде: nfcorpus с кэшем retrieval, фазы `cold` и `warm`, три повтора. Холодная фаза
должна совпасть с прогоном без кэша, тёплая — с нынешними повторами 1–2, разброс в обеих
мал. Свип c1/c2/c4/c8 одним прогоном должен дать те же точки, что четыре отдельных прогона
из ragglet-19, в пределах шума. Прошу smoke на Mac: свип с прогревом на MPS и с настоящим
Qdrant. По `per_query.warmup` будет видно, насколько велик холодный старт там.

## Вне скоупа

- Флаги попадания по запросу, точные счётчики, задержки попаданий и промахов, раздельный
  учёт кэшей, TTL и инвалидация — ragglet-22. Здесь только управляемое состояние кэша на
  старте фазы, на котором ragglet-22 будет мерить.
- Частично тёплый кэш (например, 50% запросов) и разные состояния для разных кэшей. Если
  понадобится, это расширение поля `cache` у фазы в ragglet-22.
- Обрезка переходного режима и измерение только в устойчивом окне, см. «Ограничения».
- Холодный старт процесса как метрика: свежий процесс на каждое измерение.
- Прогрев по времени и прогрев с конкурентностью. Если smoke покажет, что при c=8 первые
  запросы платят за новые TLS-соединения к LLM, у `warmup` появится `concurrency`.
- Профили как отдельные файлы, на которые ссылаются сценарии, по аналогии с профилями
  индексов. Пока профиль — это блок `run` сценария.
- Графики по фазам — ragglet-32.

## Рассмотренные альтернативы

- **Холодный и тёплый по номеру повтора**: повтор 0 холодный, остальные тёплые, как в
  статье. Работает без кода, но доля тёплых зависит от `repeats`, у холодной фазы одна
  точка без разброса, а Redis всё равно надо чистить руками.
- **Прогрев в обход кэша** вместо очистки. Холодное состояние так не воспроизводится:
  Redis с прошлого прогона и LRU с прошлого повтора остаются.
- **Очищать весь префикс модели в Redis или делать `FLUSHDB`.** Проще, но удаляет чужие
  данные: префикс общий для всех сценариев с этой моделью.
- **Одна фаза на прогон**, уровни конкурентности отдельными прогонами. Около 120 строк
  вместо 200, но без чередования и общей таблицы. Отклонено на ревью.
- **Все повторы фазы подряд, потом следующая фаза.** Тогда медленный дрейф стенда ложится
  на разницу между фазами.
- **Свежий процесс на каждую фазу.** Чисто, но меряет холодный старт процесса, а не
  архитектуру, и каждый раз заново грузит модели.

## Решено на ревью

- Фазы делаем в этой задаче: несколько измерений в одном прогоне, чередование по
  повторам, статистика по фазам (п. 5).

## Приложение: замер и детали

**Замер.** Нода агента: 2 ядра, CPU-torch 2.14.1, all-MiniLM-L6-v2, Qdrant в
local-режиме, nfcorpus test (323 запроса), `chunking: none`, `concurrency: 1`,
`shuffle: false`, три повтора, код master c4eb130. Абсолютные задержки local-режима для
выводов не годятся, важно соотношение.

| прогон | повтор | `lat_total_p50` | p95 | p99 | `lat_retrieve_p50` | `lat_embed_p50` | `throughput_qps` |
|---|---|---|---|---|---|---|---|
| без кэша | 0 | 30,4 | 96,0 | 116,9 | 6,79 | 21,6 | 27,4 |
| без кэша | 1 | 29,8 | 107,2 | 114,4 | 6,39 | 21,3 | 26,2 |
| без кэша | 2 | 29,8 | 101,8 | 114,2 | 6,46 | 21,3 | 26,4 |
| LRU | 0 | 28,9 | 107,6 | 113,9 | 5,99 | 20,8 | 26,1 |
| LRU | 1 | 10,8 | 14,8 | 30,3 | 0,09 | 10,2 | 81,4 |
| LRU | 2 | 10,8 | 12,5 | 14,7 | 0,09 | 10,1 | 90,0 |

Агрегат без кэша: p50 30,0 ± 0,3 мс, пропускная способность 26,7 ± 0,7. Агрегат с LRU:
16,9 ± 10,5 и 65,8 ± 34,7. Качество (ndcg@10 0,317) во всех повторах одинаковое.

Попутное наблюдение. В тёплых повторах эмбеддинг тоже ускорился, с 21 до 10 мс, хотя кэша
эмбеддингов в этом сценарии нет. Поэтому эффект кэша на общую задержку (18 мс) больше
сэкономленного поиска (6 мс). Вероятная причина: когда между вызовами модели нет поиска,
потоки torch не успевают уснуть, и следующий вызов не платит за их пробуждение. Мы это не
проверяли, на решение это не влияет. Но наблюдение лишний раз показывает, что холодное и
тёплое состояние надо мерить отдельными фазами, а не выводить из среднего.

**Холодный старт на ноде.** Второй запрос свежего процесса занял 78, 111 и 118 мс в трёх
прогонах из четырёх при медиане 30 мс. В четвёртом прогоне он обычный. Дальше задержки
обычные.

**Переходный режим при c=4** (прогон ragglet-19): первые пять запросов — 34, 52, 82, 113 и
102 мс, устойчивая медиана — 113.

**Пространство ключей Redis.** Ключ:
`emb:<модель>@<ревизия>:<normalize>:<id прогона>:<sha1 текста>`, id прогона — имя
каталога прогона. Очистка: `SCAN MATCH <префикс прогона>:*` и `UNLINK` пачками.

**Seed.** `random.Random` со строковым seed детерминирован между запусками и не зависит от
`PYTHONHASHSEED`: строка переводится в число через SHA-512. Модель нагрузки по-прежнему
получает целое число: `Random(f"{seed}/load/{r}").getrandbits(63)`.

**Открытая модель.** Набросок:

```python
class OpenLoad:
    class Params(BaseModel):
        model_config = ConfigDict(extra="forbid")
        rate_qps: float = Field(gt=0)
        arrivals: Literal["constant", "poisson"] = "constant"

    def __init__(self, params: Params, seed: int):
        self.params, self.rng = params, random.Random(seed)

    async def drive(self, n: int, launch: Launch) -> None:
        rate, at = self.params.rate_qps, anyio.current_time()
        async with anyio.create_task_group() as tg:
            for i in range(n):
                await anyio.sleep_until(at)
                tg.start_soon(launch, i, at)  # плановый момент, а не фактический
                at += self.rng.expovariate(rate) if self.params.arrivals == "poisson" else 1 / rate
```
