# ragglet-31 — Веб-интерфейс: каркас, редактор сценария, запуск и страница прогона

**Коротко.** SPA в `web/`: Vite + React + TypeScript, клиент генерируется из
`/v1/openapi.json`, опрос — TanStack Query, YAML — CodeMirror 6. Внешний вид не
придумывается: токены, раскладка и тексты переносятся буквально из артбордов Design-канваса
ragglet-15 в маленький свой UI-кит. Главное решение — модель редактора: **источник правды —
YAML-текст сценария**, форма — вид поверх разобранного YAML-документа (библиотека `yaml`).
Правка поля в форме меняет в тексте только значение этого поля, поэтому комментарии,
порядок и незнакомые форме ключи переживают любое число переключений «Форма ↔ YAML», а
сохранённый файл даёт в git минимальный diff. Валидность решает сервер: форма показывает
ответы `PUT` и dry-run у полей по `path`. Запуск — сохранить → dry-run → подтвердить
предупреждения → 202 → `/runs/:id`, страница прогона опрашивает `GET /v1/runs/{id}` раз в
секунду и показывает очередь, фазы, прогресс, лог, ошибку и итог. Экраны и их поведение
заданы в ragglet-15, этот документ — только про то, как фронтенд устроен.

**Что изменилось с ragglet-15.** 29 и 30 уже в master: прогоны и сборки через API
действительно выполняются, есть `GET /v1/runs` с колонками сводки, `summary`, `manifest`,
артефакты и per-query. Поэтому в 31 путь «выбрать сценарий → запустить → увидеть результат»
доходит до настоящего результата. Граница с 32 проходит по разбору результата (графики,
вкладки «Качество», «Задержки и нагрузка», «Запросы», «Условия», сравнение), а не по
наличию данных.

## Пример, на котором всё объясняется

Тот же сюжет, что в ragglet-15: из `nfcorpus_hf` сделать `nfcorpus_rerank` и запустить.
Здесь — что при этом делает фронтенд.

1. **Сценарии → `nfcorpus_hf` → Дублировать.** UI берёт `GET /v1/scenarios/nfcorpus_hf`
   (текст с комментариями и `etag`), спрашивает имя и заменяет в тексте одно значение
   `name`: строка `name: "nfcorpus_hf"` становится `name: "nfcorpus_rerank"`, остальной
   текст байт в байт тот же. `POST /v1/scenarios {yaml}` → 201, открывается
   `/scenarios/nfcorpus_rerank`.
2. **Rerank → включить, `output_top_n: 10`; Retrieval → `top_k: 50`.** Ключей `rerank.*`
   в файле не было: форма добавляет секцию `rerank:` в конец документа, комментарии
   шаблона на месте. `top_k: 30` уже был — меняется только `30` → `50`. Подсказка у
   `metrics.quality.k` («глубина финального списка — 10») считается на клиенте по
   разобранному документу и ничего не блокирует.
3. **Проверить.** `POST /v1/runs {scenario, scenario_id, dry_run: true}` с текстом из
   редактора, без сохранения: dry-run принимает конфиг содержимым, и файл на диске до
   «Сохранить» или «Запустить» не меняется. Ответ — 422,
   `issues[0].path = "metrics.quality.k"`. Путь разбирается в
   `["metrics", "quality", "k"]`, находится поле формы с этим путём: ошибка встаёт под
   ним, у секции «Метрики» красная точка, в панели «Проверка» строка, по клику — фокус на
   поле. Во вкладке YAML та же ошибка подчёркивает значение `k`: диапазон в тексте берётся
   из того же документа.
4. **Убрать 30 → Запустить.** `PUT {yaml, etag}` → 200, `valid: true`, новый `etag` →
   dry-run → 200 с одним предупреждением
   `index.not_green` (`path: null`, `where: "target default (nfcorpus_v1)"`) → диалог
   «Запустить всё равно?» → `POST /v1/runs {scenario, scenario_id}` → 202
   `{id: "nfcorpus_rerank_20261127T101540Z"}` → переход на `/runs/<id>`.
5. **Страница прогона.** `GET /v1/runs/<id>` раз в секунду, `GET /v1/tasks` раз в 2 с —
   кто впереди в очереди. `queued, position 1` → `running, phase preparing` →
   `phase progress, 120 / 323` (прошло, осталось ≈ по `progress.first_at`) → `completed`.
   Лог дочитывается `GET .../log?offset=` каждые 2 с, ANSI-коды вырезаются. После
   `completed` опрос останавливается, один раз приходит `?include=summary`, открывается
   «Обзор» в урезанном виде (решение 1 ревью): плитки nDCG@10, Recall@10, p50, p95,
   QPS, исходы и таблица повторов.

## Решение

### 1. Стек

| Что | Выбор | Почему |
|---|---|---|
| Сборка | Vite, TypeScript `strict` | стандарт для SPA, dev-сервер с прокси, `vite build` → статика |
| UI | React 19 | рекомендация ragglet-15; экосистема Query/Table/CodeMirror |
| Маршруты | React Router 7 (library mode, `createBrowserRouter`) | привычный, прямые ссылки и `?tab=`/фильтры через `useSearchParams` |
| Данные и опрос | TanStack Query 5 | `refetchInterval` от состояния, пауза в фоне, инвалидация после мутаций |
| Клиент API | `openapi-typescript` → `src/api/schema.d.ts`, `openapi-fetch` | типы путей, параметров и тел из OpenAPI; обёртка — несколько кБ, без генерации кода |
| Состояние редактора | `zustand` | один store на открытый документ, поля подписываются на свой путь |
| YAML | `yaml` (eemeli) 2.x | `parseDocument` с комментариями и диапазонами узлов, режим YAML 1.1 как у PyYAML |
| Редактор YAML | CodeMirror 6 (`@codemirror/lang-yaml`, `lint`) | лёгкий, диагностика по диапазонам; грузится лениво только на страницах редакторов |
| Таблицы | обычные `<table>` с классами артбордов | в 31 таблицы короткие, сортировка и фильтры — на сервере или в URL; TanStack Table подключит 32 для «Запросов» на тысячи строк |
| Примитивы | Radix UI: Dialog, DropdownMenu, Tooltip, Popover | доступность и фокус без дизайн-системы; стили свои |
| Стили | CSS Modules + `tokens.css` (custom properties) | токены из макетов в одном месте, без Tailwind и UI-фреймворка |
| Шрифты | `@fontsource/ibm-plex-sans`, `@fontsource/ibm-plex-mono` | локально в бандле: стенд может быть без интернета, Google Fonts не нужен |
| Тесты | Vitest, Testing Library, jsdom | работает на конфиге Vite, без отдельной сборки |
| Линт | ESLint (flat), `typescript-eslint`, `eslint-plugin-react-hooks` | минимум правил, без Prettier |

Node — 22 LTS и новее (`engines` в `package.json`), пакетный менеджер — npm,
`package-lock.json` в репозитории. Графиков в 31 нет: библиотеку (ECharts или Plotly)
выбирает 32.

### 3. Клиент API и опрос

- `npm run gen:api` поднимает `create_app()` через `uv run python -c …`, пишет OpenAPI во
  временный файл и генерирует `src/api/schema.d.ts`. Сгенерированный файл лежит в
  репозитории: сборка UI не требует Python. После правок API его перегенерируют, а
  `npm run check` (`gen:api` + `git diff --exit-code` + `tsc`) ловит устаревший клиент.
- Любой ответ не 2xx `client.ts` превращает в `ApiProblem {status, problem}`. Тело
  разбирается как `Problem` всегда, а не по схеме из OpenAPI: у шести ручек 422 объявлен
  как `HTTPValidationError`, хотя сервер отдаёт `Problem` (см. «Требования к API»). Сеть
  недоступна — `ApiProblem` со статусом 0 и сообщением «API недоступен».
- `POST /v1/runs` и `POST /v1/builds` различают 200 (отчёт dry-run) и 202 (постановка)
  по `response.status`: в OpenAPI это два разных ответа.

Интервалы опроса (`refetchIntervalInBackground: false`: скрытая вкладка браузера не
опрашивает):

| Что | Запрос | Интервал |
|---|---|---|
| Страница прогона / сборки | `GET /v1/runs/{id}`, `GET /v1/builds/{id}` без `include` | 1 с при `queued` / `running`, после — стоп |
| Лог активной задачи | `GET .../log?offset=` | 2 с, до `complete: true` |
| Полоса стенда, очередь | `GET /v1/tasks` | 2 с, если есть активная задача, иначе 10 с |
| Сервисы в шапке / на Стенде | `GET /v1/stand` | 30 с / 10 с (сервер опрашивает Qdrant и Redis) |
| Списки | `/v1/scenarios`, `/v1/runs`, `/v1/index-profiles`, `/v1/builds` | 10 с |
| Коллекции | `GET /v1/indexes` | 30 с и при возврате на вкладку |
| Открытый в редакторе документ | `GET /v1/scenarios/{id}` | не опрашивается; перечитывается при фокусе окна |
| Итог прогона | `?include=summary` | один раз после перехода в `completed` |

После мутаций (`PUT`, `POST`, `DELETE`, cancel) инвалидируются затронутые ключи: список
сценариев, `tasks`, список прогонов.

### 4. Модель редактора: текст — источник правды

Состояние открытого документа — store:

```ts
interface EditorState {
  id: string;
  text: string;                        // текущий YAML: его показывает вкладка YAML, его шлют PUT и dry-run
  saved: { text: string; etag: string; updatedAt: string };  // последняя версия с сервера
  check: CheckResult | null;           // последний ответ PUT / dry-run: проблемы, отчёт preflight
  checkedText: string | null;          // текст, к которому относится check
  touched: Set<string>;                // поля, изменённые после проверки
}
```

Из `text` мемоизированно получается `doc = parseDocument(text, {version: "1.1"})`. Режим
YAML 1.1 обязателен: сервер читает YAML через PyYAML, а в 1.1 `yes`/`off` — булевы, в 1.2
— строки. Проверено на `yaml` 2.9: результаты PyYAML и `yaml` в режиме 1.1 совпадают на
`yes`, `off`, `0o17`, а все 12 файлов `configs/scenarios` и `configs/indexes` дают
одинаковые значения в 1.1 и 1.2.

**Чтение.** Поле формы читает `doc.getIn(path)`. Ключа нет — поле пустое, а в
плейсхолдере умолчание из `meta.defaults` («по умолчанию 30»).

**Запись** идёт двумя путями.

1. *Значение уже есть в тексте и это скаляр или однострочная flow-коллекция*
   (`top_k: 30`, `k: [1, 3, 5, 10]`) — заменяется только диапазон значения
   (`node.range`), со стилем кавычек исходного узла. Остальной текст не трогается.
2. *Структурная правка*: нового ключа или секции нет в тексте, добавляется или удаляется
   элемент блочного списка (`sources`, `backends`), сбрасывается поле к умолчанию.
   Тогда `doc.setIn` / `doc.deleteIn` и `doc.toString({lineWidth: 0,
   flowCollectionPadding: false, indentSeq})`, где `indentSeq` определяется по самому
   тексту. Комментарии и незнакомые ключи сохраняются всегда, а форматирование нетронутых
   мест иногда нормализуется.

Проверено на шаблонах репозитория: путь 1 меняет ровно правленые строки во всех 12 файлах.
Путь 2 без правок воспроизводит байт в байт 10 файлов из 12. В двух оставшихся
расходятся только пробелы перед комментарием в строке (`[]   # …` → `[] # …`) и
отступ блочного списка в файле со смешанными отступами. Это приемлемо: так бывает только
при структурной правке, и комментарий остаётся на месте.

Отсюда:

- **Round-trip бесплатный.** Форма и вкладка YAML — два вида одного `text`; неизвестные
  форме ключи (`version`, `storage.routing`, будущие поля) никто не удаляет.
  Переключение вкладок ничего не пересчитывает.
- **Битый YAML.** Если `text` не разбирается, форма показывает плашку «YAML не
  разбирается: строка 12, столбец 3» и становится только для чтения. Сохранить,
  Проверить и Запустить недоступны, пока ошибку не исправят во вкладке YAML: сервер всё
  равно ответил бы 422 `config.yaml`.
- **Выключенная стадия** (`rerank.enabled: false`) сворачивается в «выключен», но её ключи
  остаются в тексте: включил обратно — значения на месте.
- **Сброс к умолчанию** у поля — удаление ключа (путь 2), а не запись умолчания: файл
  остаётся коротким, а умолчание приходит со схемой.
- **Имя.** id сценария — это `name`, переименования на сервере нет. В открытом сценарии
  `name` только для чтения, рядом «Сохранить как…»: создать копию под новым именем через
  `POST`, тем же способом, что «Дублировать».
- **Новый сценарий**, четыре способа из ragglet-15. Дублировать — замена `name` в тексте
  (путь 1). Из YAML — вставить или загрузить файл, `POST {yaml}`. Из прогона —
  `POST {from_run, name}`. Пустой — короткий скелет: `version`, `name`, `dataset`
  (`source`, `id`), `storage` (`mode: single`, `backend`) и `retrieval.sources` с одним
  vector-источником, остальное приходит умолчаниями. Полный дамп `meta.defaults` в файл не
  пишется: стена значений по умолчанию скрыла бы то, что задал человек. Сервер сохраняет
  скелет черновиком (`valid: false`), пока не заполнены `dataset.id` и коллекция.
- **Реестр полей** (`scenarioFields.ts`) — одна таблица: путь (с `[]` для элементов
  списка: `retrieval.sources[].params.ef_search`), секция, тип контрола, ограничения
  (`min`, целое), условие видимости (`rrf_k` только при `merge.method: rrf`), источник
  допустимых значений. Enum берутся из `meta.json_schema` (`Literal`-поля), а списки
  «что реализовано» — из полей meta: `retrieval_strategies`, `storage_backends`,
  `dataset_sources`, `load_models`, `metrics`, `latency_steps`. Своих списков у UI нет,
  кроме раскладки по секциям, которую ragglet-15 оставил UI. Из этой же таблицы берутся
  DOM-id полей для прокрутки к проблеме и сводка свёрнутой секции.
- **Несохранённые правки.** Это `text !== saved.text`. Уход со страницы спрашивает
  подтверждение (`beforeunload` и блокировщик роутера). Если при фокусе окна сервер
  отдал другой `etag`: без правок документ тихо перечитывается, с правками появляется
  плашка «Файл изменён вне редактора» и кнопки «Перезагрузить» и «Скопировать мой YAML».

### 5. Проблемы у полей

Источники проблем: `ConfigDocument.problem` после `PUT` (черновик, ошибки схемы), 422
dry-run и постановки (`Problem.issues`), `warnings` отчёта dry-run и `error.problem`
упавшей задачи (второй preflight). Все приводятся к одному списку `ProblemIssue` и
привязываются так:

1. `path` разбирается в сегменты; индексы списков — числа.
2. Ищется поле реестра с этим путём (индекс совпадает с `[]` шаблона). Нашлось — проблема
   под полем; для элемента списка — под полем нужной карточки (`sources[1]`).
3. Не нашлось — путь укорачивается с конца, пока не найдётся поле или группа реестра:
   `retrieval.sources[1].params` → карточка источника 1, `storage.backends` → блок целей
   хранилища, `rerank` → секция Rerank.
4. Корень пути неизвестен форме (`config.extra_forbidden` с `path: bogus`) или
   `path: null` — проблема идёт в секцию «Датасет и индекс» (решение 3 ragglet-15) и в
   панель.

Каждая проблема попадает в панель «Проверка». Клик раскрывает секцию, прокручивает к полю
и ставит фокус; если поля нет, открывается вкладка YAML на нужной строке. Во вкладке YAML
проблемы с `path` подчёркивают диапазон узла (`doc.getIn(path, true).range`), а
`config.yaml` с `where: "line 3, column 2"` — эту позицию. Это диагностика
CodeMirror `lint`. Ошибки разбора YAML показываются там же, локально и сразу, ещё до
сервера.

Устаревание: проверка относится к `checkedText`. Проблема у поля скрывается, как только это
поле изменили (`touched`): она была про старое значение. Остальные остаются до следующей
проверки, а у панели появляется пометка «текст изменён после проверки». Точки секций
считаются по видимым проблемам: красная — есть `error`, жёлтая — только `warning`.

### 6. Подсказки формы

`hints(doc) → Hint[]` — чистая функция над разобранным документом. Подсказка только
показывается и ничего не блокирует:

- глубина финального списка `min(top_k, input_top_k, output_top_n)` и какие `k` её
  превышают (при выключенном rerank — `top_k`);
- `rerank.input_top_k > retrieval.top_k`;
- сумма `retrieval_ms + rerank_ms + llm_ms` (по включённым стадиям) больше `total_ms`;
- `single` и больше одного источника (ядро берёт `sources[0]`); `keyword` при `single`;
  больше одного `keyword`;
- включение generation включает context, и форма об этом сообщает;
- датасет выбранной коллекции ≠ `dataset`; `embedding` ≠ модель коллекции;
- в профиле: `chunk_overlap >= chunk_size`.

### 7. Запуск

Кнопка «Запустить» — конечный автомат в `editor/launch.ts`. «Проверить» — его шаг
`checking` сам по себе: dry-run текущего текста без сохранения. «Повторить» и «Запустить
выбранные» проходят тот же автомат без шага сохранения.

```
saving ──PUT {yaml, etag}──► checking ──dry-run──► confirming ──► submitting ──202──► /runs/:id
  │ 409 → «Файл изменён вне редактора»   │ 422 → проблемы у полей     │ warnings → «Запустить всё равно?»
  │ 422 config.yaml / name_mismatch      │ (стоп)                     │ нет warnings → сразу дальше
  │ 200 valid:false → проблемы (стоп)                                 │ 422 при постановке → как dry-run
```

- **Сохранение** пропускается, если `text === saved.text`. Если `PUT` вернул
  `valid: false`, dry-run не делается: схема не прошла, и сервер ответил бы той же 422.
- **409** — диалог «Файл изменён вне редактора» со временем правки из ответа:
  «Перезагрузить (правки потеряются)», «Скопировать мой YAML», «Отмена». Слияния нет.
- **Предупреждения** dry-run показываются в диалоге списком. Постановка (без `dry_run`)
  делает preflight ещё раз; если там 422 (индекс пересобрали между проверкой и запуском),
  автомат возвращается в состояние «проблемы».
- **«Повторить»** на странице прогона: `GET ?include=scenario` → dry-run →
  подтверждение → `POST {scenario: scenario_yaml, scenario_id}`.
- **«Запустить выбранные»** в списке сценариев: тексты через `GET`, затем по одному
  dry-run на сценарий, по порядку (сервер всё равно проверяет по одному). Диалог
  показывает по каждому «готов / предупреждения / ошибки»; запускаются отмеченные, не
  прошедшие остаются в диалоге со своими проблемами и ссылкой в редактор.

### 8. Страница прогона `/runs/:id`

Одна страница во всех состояниях, данные — `RunStatus` без `include`:

| Состояние | Тело |
|---|---|
| `queued` | позиция и задачи впереди (из `/v1/tasks`, с прогрессом текущей), предупреждения постановки, план: `repeats × queries_per_repeat`, нагрузка |
| `running` | шаги «В очереди → Подготовка → Запросы → Завершение» по `phase`; полоса `done / total`, повтор `⌊(done − 1) / queries_per_repeat⌋ + 1` из `repeats`, прошло (от `started_at`, тикает локально), осталось ≈, скорость ≈; хвост лога |
| `failed` | красная плашка: `error.type`, `message`, `qid`; если есть `error.problem` — список проблем и «Открыть в редакторе» с подсветкой полей (проблемы передаются в состоянии навигации) |
| `cancelled` | «отменён в 12:40, выполнено 420 / 969» из `finished_at` и `progress` |
| `completed` | вкладки результата, по умолчанию «Обзор» |

- **Осталось ≈** — линейно по средней скорости между `progress.first_at` и
  `progress.updated_at`. Пока событий мало (меньше 3 с от первого) — «оценивается…».
  Формулы `eta.ts` покрыты тестами, включая `done == total` и `done == 0`.
- **Лог** — свой хук, а не `useQuery`: смещение копится, текст дописывается,
  ANSI-последовательности вырезаются (transformers красит вывод и без tty, заметка
  ragglet-35). Автопрокрутка, пока пользователь внизу. В памяти не больше 1 МиБ; дальше
  начало обрезается с пометкой «начало — в файле `task.log`» и ссылкой на артефакт. Для
  завершённой задачи лог читается до `complete: true` и больше не опрашивается.
- **Отменить** — подтверждение, `POST .../cancel`; 409 `task.finished` — просто
  перечитать статус.
- **Шапка**: сценарий со статусом файла (`scenario_file`: изменён после прогона, удалён),
  `origin: import` — «прогон из CLI» (у таких нет `plan` и `etag`, страница это
  выдерживает), датасет, коллекция, теги, времена. Действия: Отменить, Повторить, Открыть
  как сценарий (`POST /v1/scenarios {from_run, name}`), Скачать (`artifacts.zip`).
- **Вкладки — реестр** `run/tabs.ts`: `{id, title, available(status), Component}`; вкладка
  в URL (`?tab=`). В 31: **Обзор** в урезанном виде (решение 1 ревью):
  верхний ряд плиток артборда `RunOverview` из `summary.aggregate` с `± std` и
  таблица «Повторы» из `summary.repeats`, без графиков. Ещё **Конфиг** (snapshot из
  `include=scenario`, только чтение, тот же CodeMirror), **Лог**, **Файлы** (список
  артефактов, ссылки, zip). Вкладки 32 видны в той же полосе как неактивные с подписью
  «ragglet-32»: 32 добавляет записи в реестр и графики в «Обзор», не трогая страницу.

Страница сборки `/builds/:id` собрана из тех же частей (шапка задачи, шаги фаз с
`progress("corpus", …)`, лог, отмена) плюс результат: цели, документы, записанные
метаданные. Упавшая сборка прямо говорит, что коллекция осталась без метаданных, и
предлагает пересобрать.

### 9. Остальные экраны — коротко

  `/v1/tasks` закреплены сверху. Чекбоксы есть, «Сравнить» неактивна с подписью
  «ragglet-32».
- **Индексы**: вкладка «Коллекции» (`GET /v1/indexes`: состояние, датасет, модель,
  chunking, points, кто использует; «Метаданные» — JSON в диалоге; «Пересобрать» —
  профиль из `profiles`) и вкладка «Профили» (`GET /v1/index-profiles`).
- **Редактор профиля** — тот же `editor/` с реестром `profileFields.ts`. «Собрать» — тот

  `BuildCheck.targets` (существует ли коллекция, points, `built_at`, `used_by`), затем
  `POST` → `/builds/:id`.
- **Секция «Датасет и индекс»** в редакторе сценария: выбор коллекции из `GET /v1/indexes`
  заполняет `storage.backend.{endpoint, collection}` и `embedding.{model, normalize}` из
  метаданных `ragglet` коллекции (поля «из индекса», с кнопкой «задать вручную»). Если
  датасет пуст или отличается, форма предлагает датасет коллекции. Для
  `sharded`/`replicated` — список коллекций в `backends[]`. `dataset.id` — поле с
  подсказками из `GET /v1/datasets` (локальные каталоги со сплитами, `hf`-id).

### 11. Сборка, разработка, раздача

- **Разработка**: `python3 ragglet start` (лаунчер ragglet-37) и `cd web && npm run dev`. Vite на `:5173`
  проксирует `/v1` на `http://127.0.0.1:8000` (`RAGGLET_API_URL` меняет адрес). Origin
  один, CORS не нужен.
- **Сборка**: `cd web && npm ci && npm run build` → `web/dist` (ассеты с хэшами в
  `dist/assets/`). `python3 ragglet start` (решение 7 ревью) собирает UI сам, если `web/dist`
  нет или исходники `web/` новее: `npm ci` — только при новом `package-lock.json`, вывод — в
  `results/web.log`; без Node.js 22+ или при ошибке сборки сервер стартует без UI, `--no-ui`
  пропускает шаг. Сборка в git не коммитится. Раздача: `start` подставляет
  `RAGGLET_UI_DIR=web/dist`, если UI собран (без лаунчера — `RAGGLET_UI_DIR=web/dist uv run python -m ragglet.server`)
  → `http://127.0.0.1:8000/`, `--open` открывает браузер. `SpaStaticFiles` уже отдаёт `index.html` на прямые
  ссылки вроде `/runs/<id>?tab=log`. Правок Python не нужно.
- **`.gitignore`**: добавляется `node_modules/`; `dist/` уже игнорируется общим правилом.
- **README**: раздел «Веб-интерфейс» — сборка, запуск, разработка, `npm test`,
  `npm run gen:api`.
- **Docker (ragglet-34)** — вне скоупа, но путь прямой: стадия `node:22` делает
  `npm ci && npm run build`, `web/dist` копируется в образ, `RAGGLET_UI_DIR` указывает на
  него.

## Требования к API

Блокирующих нет: всё, что нужно 31, в API уже есть. Мелкое, по желанию владельцев 28/30:

1. **422 в OpenAPI.** У `GET /v1/runs/{id}`, `POST /v1/runs/{id}/cancel`,
   `GET /v1/runs/{id}/log` и трёх таких же ручек сборок 422 объявлен как FastAPI-шный
   `HTTPValidationError`, хотя сервер отдаёт `Problem`. Нужен
   `responses={422: {"model": Problem}}` (или общий `ERRORS`). Клиент это не ломает: он
   разбирает любой не-2xx как `Problem`.
2. **201 у `PUT /v1/scenarios/{id}` и `/v1/index-profiles/{id}`** при создании файла не
   объявлен в OpenAPI (только 200). Клиент считает успехом любой 2xx.
3. **Описания полей схемы.** `Field(description=…)` есть у немногих полей
   (`run.repeats`, `run.shuffle`, …). Если их добавить в `config/scenario.py`, форма
   покажет их как подсказки вместо своих текстов, и CLI-документация получит их тоже. Пока
   подсказки к полям написаны в реестре UI.
4. **Чипы конвейера.** В `Pipeline` списка сценариев нет метода слияния, видов источников и
   `storage.mode`, поэтому чипов `rrf`, `weighted_sum`, `bm25`, `sharded` с артборда
   `Scenarios` в UI нет. Хватит трёх полей в `Pipeline`.
5. **Строки упавших и отменённых прогонов.** В `RunItem` нет `error` (класс и сообщение) и
   `final_progress`. Поэтому в списке прогонов вместо «index.no_metadata: …» и
   «выполнено 210 / 500» с артборда `Runs` стоит «—».

   store, секции формы, вкладка YAML с диагностикой, Сохранить (409, черновики),
   Проверить, панель «Проверка», выбор коллекции и датасета.
4. **Запуск и прогон.** Автомат запуска, страница прогона во всех состояниях (очередь,
   фазы, прогресс, лог, отмена, ошибка, урезанный Обзор, Конфиг, Файлы), Повторить, Открыть как
   сценарий, список прогонов, «Запустить выбранные».
5. **Профили индексов и сборка.** Редактор профиля на общем `editor/`, проверка и диалог
   «Будут пересозданы», страница сборки.

Каждый этап заканчивается `npm run check`, `npm test` и ручной проверкой против
настоящего сервера (Qdrant и Redis на Mac): во встроенном браузере проходится путь
этапа.

## Отклонения от артбордов (найдено при реализации)

- **Чипы конвейера и строки упавших прогонов** — неполнее артбордов: этих данных нет в API
  (пункты 4 и 5 «Требований к API»).
- **Длинные тексты.** Реальные описания сценариев длиннее, чем на артборде `Scenarios`:
  описание обрезается до двух строк, полный текст — во всплывающей подсказке. Отступы ячеек
  в широких таблицах — 9 px вместо 12, чтобы таблица помещалась в 1360 px без прокрутки.
- **Имя в редакторе** только для чтения (§4), а не поле ввода, как на артборде
  `ScenarioEditor`. Переименование — «Сохранить как…».
- **«Условия на старте»** на странице идущего прогона показывают то, что есть в статусе:
  датасет, коллекцию, план, нагрузку, предупреждения, следующую задачу. Модель, rerank и
  окружение лежат в `manifest`; их структурно покажет вкладка «Условия» (32).
- **«Кэш» в «Обзоре»** определяется по snapshot сценария (`cache.enabled` и слои): в summary
  `emb_hit_rate` и `ret_hit_rate` равны 0 и при выключенном кэше.
- **Чипы состояний** над списком прогонов — без счётчиков: ради чисел понадобились бы
  отдельные запросы.

## Тесты (критерий приёмки)

`npm run check` (свежий `schema.d.ts`, `tsc --noEmit`, ESLint) и `npm test` (Vitest):

1. **`yamlDoc`** на всех файлах `configs/scenarios` и `configs/indexes` (читаются из
   репозитория): разбор без правок сохраняет текст; правка существующего скаляра меняет
   ровно одну строку; правка flow-списка `k` — одну строку; добавление ключа и секции,
   удаление элемента `sources` сохраняют все комментарии и незнакомые ключи
   (`version`, `storage.routing`, выдуманный `x_custom`); `yes`/`off` читаются как в PyYAML;
   замена `name` при дублировании меняет одну строку.
2. **`paths` и `issues`** — таблица случаев: `metrics.quality.k` → поле;
   `retrieval.sources[1].params.backend_ref` → поле карточки 1;
   `retrieval.sources[1].params` → карточка; `storage.backends` → блок; `rerank` →
   секция; `bogus` и `null` → «Датасет и индекс» и панель; `config.yaml` с
   `where: "line 3, column 2"` → позиция в YAML. Поле, изменённое после проверки, теряет
   свою проблему, остальные — нет.
3. **`hints`**: глубина списка с rerank и без, `k` больше глубины, бюджеты таймаутов,
   `single` с двумя источниками, `overlap >= size` в профиле.
4. **`eta`, фазы и повтор**: `done = 0`, первые секунды, `done = total`, номер повтора
   на границах `queries_per_repeat`; `ansi` вырезает цвет и курсор.
5. **Автомат запуска** на заглушке клиента: без правок `PUT` не идёт; 409 → состояние
   конфликта; `valid: false` → стоп без dry-run; dry-run 422 → проблемы; 200 с
   предупреждениями → подтверждение; 202 → переход с id; 422 при постановке → проблемы.
6. **Компоненты** (Testing Library): ответ 422 ставит ошибку под полем `k` и точку у
   секции; клик в панели фокусирует поле; страница прогона на последовательности
   ответов `queued → running/preparing → progress → completed` показывает нужные блоки и
   останавливает опрос.

e2e в CI нет: в репозитории нет CI, а сквозной путь требует Qdrant и собранного индекса,
как `integration`-тесты ragglet-35. Вместо него — ручной чек-лист в PR: Дублировать →
изменить → Проверить с ошибкой → исправить → Запустить → очередь → фазы → готово →
Обзор; отмена; упавший прогон; сборка `demo`. Playwright-смоука нет (решение 3 ревью).

## Вне скоупа

- Всё из «Что остаётся 32»; Парето (33); Docker-образ с UI (34).
- Мобильная вёрстка, языки сверх русского и английского.
- История правок (undo) формы сверх «Сбросить к сохранённому»; в YAML-вкладке undo
  CodeMirror есть.
- Diff сценария с исходником и diff snapshot с текущим сценарием (ragglet-15 разрешил
  «по желанию в 31» — не берём: путь запуска важнее).
- Слияние при 409 — только перезагрузка или копия своего текста.
- SSE, перестановка очереди, удаление прогонов и коллекций — как в ragglet-15.

## Рассмотренные альтернативы

- **Состояние — JS-объект конфига, YAML — его дамп** (react-hook-form / свой объект +
  `js-yaml`). Отвергнуто: при каждом переключении вкладок пропадают комментарии шаблонов,
  меняется порядок ключей, а незнакомые ключи надо отдельно сливать обратно. Две модели
  данных пришлось бы синхронизировать. Текст как источник правды делает round-trip
  тривиальным.
- **Всегда пересериализовать документ целиком** (`toString` на каждую правку). Проще на
  одну функцию, но первая же правка поля в двух шаблонах меняет посторонние строки, и diff
  в git шумит. Точечная замена диапазона — два десятка строк кода с тестом.
- **Форма из JSON Schema** (rjsf) — отвергнута в ragglet-15.
- **Monaco** вместо CodeMirror — мегабайты и web-workers ради одного YAML-поля.
- **Дизайн-система** (MUI, Mantine, Chakra) или Tailwind — тяжелее и навязывает свой вид.
  Макеты уже задают маленький набор компонентов, его проще написать на токенах.
- **TanStack Router** вместо React Router — типизированные search params пригодились бы
  фильтрам 32, но это лишняя для одного пользователя сложность. Разбор параметров —
  маленькие функции рядом со страницами.
- **Сгенерированные хуки** (orval, openapi-generator) — тяжелее, генерируют код, который
  потом не хочется читать. `openapi-fetch` даёт те же типы без генерации кода.
- **Собранный `web/dist` в репозитории**, чтобы сервер показывал UI без Node.
  Отвергнуто: артефакты сборки в git, конфликты при каждом изменении. Без Node UI получают
  из Docker (34).
- **Черновик правок в `localStorage`** — не нужен: черновик сохраняется на сервер
  (`valid: false`), и его видит CLI (решение ragglet-28).

## Решено на ревью

1. **Результат в 31 — урезанный «Обзор».** Из артборда `RunOverview` в 31 берутся только
   верхний ряд плиток и таблица «Повторы» из `summary`, без графиков. Остальное на этом
   артборде и прочие вкладки результата остаются 32.
2. **Список прогонов делается в 31** (этап 4): после 30 он дешёвый — таблица над
   `GET /v1/runs` с фильтрами в URL.
3. **Playwright-смоука нет.** Сквозной путь проверяется по ручному чек-листу.
4. **Тёмная тема — в 31** (после ручной проверки): на тех же токенах, с переключателем и
   режимом «как в системе» (§10).
5. **Английская версия UI — в 31**, с переключателем RU / EN (§10).
6. **Навигация по секциям редактора — оглавление** (комментарий на канвасе): подсвечена одна
   секция, которая сейчас на экране, а не все раскрытые; выключенные стадии помечены «выкл».
   Раскрыта секция или нет, видно по самой секции.
7. **UI собирает `python3 ragglet start`** (§11): сборка у пользователя, а не в git; шаг
   пропускается без Node.js и при свежей сборке. Для тех, у кого Node.js нет, UI соберёт
   Docker-образ (ragglet-34, multi-stage).
