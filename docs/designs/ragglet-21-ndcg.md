# ragglet-21 — nDCG@k и graded relevance

## Контекст

После ragglet-16 и ragglet-17 большая часть основы уже готова:

- qrels хранят grades: `QueryItem.qrels: dict[str, int]` (только score > 0);
- оценка строится через `Ranking(grades, ideal)` и реестр `METRICS`, флаг `needs_ideal`
  закрывает doc-only метрики на chunk-level;
- `eval_sha256` хэширует grades, поэтому graded-метрики двух прогонов сравнимы при тех же
  условиях, что и бинарные: сверять хэш отдельно не нужно.

Пока grade используется только как `> 0`. Градуированная разметка встречается на практике:
в BeIR/nfcorpus test 323 запроса, 11 758 пар с оценкой 1 и 576 с оценкой 2, у 119 запросов
есть документы с оценкой 2. Бинарные метрики не видят, какой из релевантных документов
стоит выше.

## Решение

### 1. `ndcg@k`

```
DCG@k  = Σ_{i ≤ k} gain(u_i) / log2(i + 1)        # i — ранг с 1, после дедупа
IDCG@k = то же по Ranking.ideal (все grades из qrels по убыванию), обрезанному до k
nDCG@k = DCG@k / IDCG@k;  IDCG = 0 → 0
```

- **Линейный gain = grade**, как `ndcg_cut` в trec_eval/pytrec_eval, через которые
  считают BEIR и MTEB. Я сверил на graded-примере (п. «Тесты», пример 1): совпадение
  с pytrec_eval до 1e-6. Экспоненциальный gain `2^g − 1` (Burges et al.) на том же примере
  даёт 0.395 вместо 0.434, то есть числа несравнимы с публикациями. Ручку выбора gain не
  добавляем; другой вариант при необходимости станет отдельной записью в реестре.
- Grade ≤ 0 даёт gain 0: в `qrels` такие пары не попадают.
- Метрика **только для doc-level** (`needs_ideal=True`). На chunk-level ideal неизвестен,
  и существующая валидация конфига выдаёт понятную ошибку.
- Ранг задаётся порядком финального списка (после rerank/context), ничья по score не
  пересортировывается. trec_eval при равных score сортирует по docno, но у нас порядок
  определяет пайплайн, а не один score.
- Doc-дедуп (MaxP из ragglet-16) гарантирует `nDCG ≤ 1`: без него один документ дал бы
  свой gain несколько раз.

### 2. `r_cap@k` (перенесён сюда из ragglet-16)

`r_cap@k = |релевантные в топ-k| / min(k, |R|)`, это `R_cap@k` из BEIR. При `|R| ≤ k`
совпадает с recall, при `|R| > k` совпадает с precision. Нужен на датасетах с большим
числом релевантных: на nfcorpus их в среднем ~38 на запрос, и `recall@10` там ограничен
сверху значением 10/38 ≈ 0.26. Помечается `needs_ideal=True`, включается явно.

### 3. Бинарные метрики при graded qrels

`recall`, `hit`, `mrr`, `precision` и `r_cap` считают релевантным grade > 0 (как
`relevance_level=1` в pytrec_eval), величина grade на них не влияет. Сама семантика
исправлена в ragglet-16 (Recall ≠ Hit). Здесь её только документируем рядом с nDCG,
это и есть «уточнённые» метрики из формулировки задачи.

### 4. Когда релевантных документов нет

| Случай | Поведение |
|---|---|
| У запроса в split есть только оценки ≤ 0 | Как и сейчас (`eval_items`), запрос исключается из eval-набора. **Новое:** dataset-warning `qrels.no_relevant` для каждого такого запроса. |
| Финальный список пуст (timeout, пустой индекс) | Все метрики 0, запрос засчитан как промах, как сейчас. |
| `ideal` пуст при прямом вызове функции | 0.0, как в pytrec_eval. В бенче этот случай недостижим, значение фиксирует контракт функции. |

Почему warning: BEIR (через pytrec_eval) оставляет такие запросы в среднем с нулями по
всем метрикам, а мы усредняем по меньшему числу запросов. Значит, на таких датасетах наше
среднее будет выше опубликованного, и warning делает это расхождение видимым. На demo и
nfcorpus таких запросов нет.

### 5. Переход chunk → doc

- **doc-level:** документ занимает ранг лучшего своего чанка (MaxP) и получает grade из
  qrels. Graded-разметка проекцию не меняет.
- **chunk-level:** чанк наследует grade документа. Метрики, доступные на этом уровне
  (`hit`, `mrr`, `precision`), смотрят только на `grade > 0`, поэтому grade на chunk-level
  пока ни на что не влияет.
- Отклонено: graded-метрика на chunk-level, нормированная на идеальную перестановку
  найденных чанков («локальный» nDCG). Она оценивает только порядок внутри выдачи и не
  замечает пропущенных документов, а при разном `top_k` вводит в заблуждение.

### 6. Конфиг и колонки

- В реестр добавляются `ndcg` и `r_cap`.
- Значение по умолчанию: `doc: [ndcg, recall, hit, mrr]`. nDCG@10 — главная метрика
  BEIR/MTEB, и она нужна для Парето-анализа (ragglet-33).
- Колонки `doc_ndcg@k` и `doc_r_cap@k`, в summary `<колонка>_mean`, в агрегате по
  повторам они появляются автоматически. `evaluation.py`, `query_loop.py` и `summarize.py`
  не меняются: они работают через реестр.
- В `configs/scenarios/*.yaml` в явные списки добавляется `ndcg`, в `nfcorpus_hf.yaml`
  ещё и `r_cap`. Конфиги статьи (`configs/experiments/article/*`) не трогаем.

### 7. Документация семантики

Новый `docs/metrics.md` — одно место для всех метрик:
- таблица формул (recall, hit, mrr, precision, ndcg, r_cap);
- уровни doc/chunk и дедуп;
- граничные случаи из п. 4;
- отличия от BEIR/pytrec_eval: ничьи и запросы без релевантных.

README, `docs/config-reference.yaml` и `docs/architecure-and-current-state.md` получают
по строке со ссылкой на этот документ.

### Почему не pytrec_eval / ir_measures как зависимость

Мы оцениваем собственное ранжирование: с doc-дедупом, chunk-level и порядком,
который задаёт пайплайн. Библиотеке пришлось бы подавать фиктивные score, а ничьи она
пересортирует по docno. Формулы занимают около 10 строк. pytrec_eval используется один раз,
вне репозитория, чтобы сверить golden-значения тестов.

## Тесты (критерий приёмки)

Golden-значения заранее посчитаны и сверены с pytrec_eval:

1. **Graded:** qrels `{d1: 2, d2: 1, d3: 1, d4: 2}`, список `[x, d2, d1, y, d3]` даёт
   `ndcg@3 = 0.433544`, `ndcg@5 = 0.481280`, `recall@5 = 0.75`, `precision@5 = 0.6`,
   `mrr = 0.5`, `r_cap@3 = 2/3`, `r_cap@5 = 0.75`.
2. Идеальный порядок даёт 1.0. Если поменять местами документы с grade 2 и 1, nDCG < 1,
   а `hit`, `recall` и `mrr` не меняются: только nDCG видит grade.
3. Бинарный случай, один релевантный документ на ранге r: `ndcg@k = 1 / log2(r + 1)`.
4. Граничные случаи: пустой `ideal` → 0; пустой список → 0; при `|R| > k` IDCG
   обрезается до k.
5. Дедуп: `[d1#0, d1#1, d2#0]` при `{d1: 2, d2: 1}` даёт doc `ndcg = 1.0`, а не больше 1.
6. `r_cap` равен `recall` при `|R| ≤ k` и `precision` при `|R| > k`.
7. Конфиг: `ndcg`/`r_cap` на chunk-level дают ошибку валидации; колонки по умолчанию
   включают `doc_ndcg@k`.
8. Датасет: запрос только с оценками 0 даёт warning `qrels.no_relevant` и не попадает
   в eval-набор.
9. `tests/test_configs.py` проходит на всех закоммиченных конфигах.

E2E (цифры положу в PR):

- near-E2E на demo с фейковым эмбеддером и локальным Qdrant: новые колонки есть в
  per_query, summary и агрегате.
- **Ориентир на реальных данных.** Прогон: BeIR/nfcorpus test, all-MiniLM-L6-v2,
  `chunking.method: none` (документ целиком, как в MTEB). Ожидаемые значения, по
  [официальным результатам MTEB](https://github.com/embeddings-benchmark/results/blob/main/results/sentence-transformers__all-MiniLM-L6-v2/8b3219a92973c328a8e22fadcfa821b5dc75636a/NFCorpus.json):
  - `doc_ndcg@10 ≈ 0.316`;
  - `doc_mrr@10 ≈ 0.505`;
  - `doc_recall@10 ≈ 0.155`.

  Небольшое расхождение допустимо: у нас HNSW вместо точного поиска и другая склейка
  title + text. Прогон проверяет весь пайплайн, а не только формулу. Нужны torch и Qdrant:
  попробую на агентской ноде с CPU-torch в отдельном venv, а если не хватит памяти, попрошу
  прогнать локально.

## Вне скоупа

- Экспоненциальный gain, MAP.
- Метрики по стадиям (retrieval против финального списка).
- Span-level релевантность чанков.
- Статистическая значимость различий.
