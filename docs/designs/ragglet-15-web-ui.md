# ragglet-15 — Веб-интерфейс стенда: экраны, состояния и требования к API

**Коротко.** Веб-интерфейс — клиент единого API (ragglet-38) для одного исследователя.
Через него делается всё, что сейчас делается из терминала и редактора YAML: собрать
индекс, настроить сценарий, проверить его, запустить, следить за очередью и прогрессом,
разобрать результат прогона. Четыре раздела: Стенд, Сценарии, Индексы, Прогоны.
Сценарий редактируется формой, собранной по стадиям конвейера, с YAML рядом; валиден ли
он, решает сервер через dry-run, форма только показывает ответ у нужных полей. Главный
экран — страница прогона: один URL от постановки в очередь до результатов, с состояниями
«в очереди → подготовка → запросы → завершение → готово / ошибка / отменён».
Сравнение прогонов и Парето (ragglet-32, 33) не входят, но реестр и страница прогона
спроектированы так, чтобы сравнение добавилось без переделки. Этот документ — требования
к 28, 29 и 30 со стороны UI; реализация самого UI — в 31 (настройка и запуск) и 32
(графики). Все endpoints ниже — кандидаты: имена и схемы решаются в 28.

Макеты экранов (восемь артбордов, переходы между ними — ссылками):
<https://claude.ai/artifact/Js6mG6wkfRbEwxmeadJGs4>. Числа на макетах взяты из прогона
`nfcorpus_hf_20261024T180917Z` и дорисованы для примера с реранком; это иллюстрация, не
результат.

## Пример, на котором всё объясняется

Исследователь хочет узнать, помогает ли реранк на nfcorpus. Индекс `nfcorpus_v1` уже
собран, прогон без реранка (`nfcorpus_hf`) уже был.

1. **Сценарии → `nfcorpus_hf` → Дублировать.** Новый сценарий `nfcorpus_rerank`
   открывается в редакторе. Секция «Датасет и индекс» показывает выбранную коллекцию
   `nfcorpus_v1`: датасет `hf:BeIR/nfcorpus`, модель `all-MiniLM-L6-v2`, chunking
   `recursive 800/120`, статус `green`, 9 696 points.
2. В секции **Rerank** включает реранк, выбирает `cross-encoder/ms-marco-MiniLM-L-6-v2`,
   ставит `input_top_k: 50`, `output_top_n: 10`; в **Retrieval** поднимает `top_k` до 50.
   Рядом с `metrics.quality.k` форма сразу пишет подсказку: «глубина финального списка —
   10 (`rerank.output_top_n`)», а значение `30` в списке `k` подсвечено жёлтым.
3. **Проверить.** Сервер отвечает 422 с одной ошибкой:
   `metrics.quality.k=30 exceeds final list depth 10 (rerank.output_top_n)`. Ошибка
   встаёт под полем `k`, секция «Метрики» в левой колонке получает красную точку.
   Исследователь убирает 30, проверяет снова. Теперь 200 и отчёт preflight: датасет,
   ревизия, хэши, индекс, «323 запроса × 1 повтор, concurrency 16» и одно
   предупреждение `index.not_green`: коллекция `yellow` — Qdrant ещё оптимизирует её
   после недавней пересборки.
4. **Запустить.** Диалог: «Предупреждения preflight: … Запустить всё равно?». Да.
   Сценарий сохраняется, сервер отвечает 202, UI открывает `/runs/<id>`.
5. **Страница прогона, «В очереди».** Впереди сборка `demo_sharded`, 12 400 / 50 000
   документов. Через минуту сборка кончается, прогон переходит в «Подготовка» (сервер
   грузит cross-encoder, у ядра для этого нет события прогресса), затем «Запросы»:
   полоса `120 / 323`, прошло 0:41, осталось ≈ 1:10.
6. **Готово.** Обзор: nDCG@10 `0,331`, Recall@10 `0,154`, p50 `318 мс`, p95 `1 180 мс`,
   QPS `9,4`, исходы `316 ok · 7 timeout · 0 error`. Полоса задержек по стадиям: реранк
   занимает три четверти p50. Таблица таймаутов по стадиям: все 7 — `rerank`.
7. **Запросы**, фильтр `outcome = timeout`. Это длинные запросы с 50 кандидатами, у всех
   `lat_rerank_ms` пустой, `lat_total_ms` упёрся в `timeouts.total_ms`. Вывод за пять
   минут вместо чтения CSV: `timeouts.rerank_ms: 800` мал для top-50 на CPU, и это
   обязательно учесть при сравнении с базой — иначе 2 % промахов будут выглядеть как
   «реранк хуже».
8. **Открыть как сценарий** из вкладки «Конфиг» → новый сценарий из snapshot прогона,
   `rerank_ms: 2000` → Запустить. Второй прогон встаёт в очередь.

Ни один шаг не требовал терминала, YAML видно во вкладке рядом с формой, и каждое
действие прошло через тот же API, что и `ragglet bench run`.

## Кто пользователь и что он делает

Один человек, исследователь, на одном стенде. Авторизации, ролей и поля «кто запустил»
нет. Что он делает, в порядке частоты:

| # | Задача | Где в UI |
|---|---|---|
| U1 | Посмотреть, чем занят стенд и что закончилось за ночь | Стенд, Прогоны |
| U2 | Сделать вариант сценария (клон + одно-два изменения), проверить, запустить | Сценарии → редактор |
| U3 | Поставить серию прогонов подряд (S0–S5 на одном индексе) | Сценарии, «Запустить выбранные» |
| U4 | Следить за прогоном, отменить, если что-то не так | Прогон, Стенд |
| U5 | Разобрать результат: качество, задержки, нагрузка, кэш, аномалии, условия | Прогон |
| U6 | Собрать или пересобрать индекс с другим chunking или моделью | Индексы → профиль → сборка |
| U7 | Экспортировать: YAML сценария, файлы артефактов, таблицы для статьи | Редактор, Прогон → Файлы |
| U8 | Воспроизвести прогон: повторить как есть или взять snapshot за основу | Прогон → Повторить / Открыть как сценарий |

Сравнение двух прогонов (U9) — ragglet-32, в этом документе только задел под него.

## Решения

### 1. Четыре раздела, задача — не отдельный раздел

Навигация: **Стенд · Сценарии · Индексы · Прогоны**. Задачи менеджера (29) не
показываются как отдельная сущность: прогон — это страница прогона, сборка — страница
сборки, очередь и текущая задача видны на Стенде и в шапке. Пользователь думает про
прогоны и индексы, а не про jobs.

В шапке на всех страницах — полоса состояния стенда: «Свободен» или «Прогон
`nfcorpus_rerank` · 120 / 323 · ещё 2 в очереди», плюс точки доступности Qdrant и Redis.
Клик ведёт на активную задачу.

### 2. Библиотека сценариев и профилей — каталог на сервере

Сценарии хранятся там же, где сейчас: `configs/scenarios/*.yaml`; профили индексов — в
`configs/indexes/*.yaml`. API читает и пишет эти файлы, UI их никогда не видит как файлы.
Идентификатор сценария — имя файла без расширения, и оно равно полю `name` внутри
(`name` — функциональное поле: имя каталога прогона и часть ключа retrieval-кэша, поэтому
UI ограничивает его `[A-Za-z0-9_-]`).

Почему каталог, а не таблица в реестре:
- CLI (`ragglet bench run configs/scenarios/x.yaml`) и UI работают с одной и той же
  библиотекой; сохранённый в UI сценарий можно закоммитить.
- Шаблоны S0–S5 — это и есть начальное содержимое библиотеки, отдельной сущности
  «шаблон» не нужно.
- У прогона есть собственный неизменяемый `scenario.snapshot.*`, так что библиотека может
  быть изменяемой без потери воспроизводимости.

Чтобы два редактора (UI и IDE) не затирали друг друга молча, API отдаёт `updated_at` и
принимает его в `If-Match`-стиле: сохранение поверх изменённого файла — 409, UI
предлагает перезагрузить. `configs/experiments/**` в библиотеку не входит.

Новый сценарий создаётся четырьмя способами: дублировать существующий, из YAML (вставить
или загрузить), из snapshot прогона, пустой (defaults схемы: невалиден до заполнения
`name`, `dataset`, `storage`).

### 3. Форма по стадиям конвейера, YAML рядом, валидность решает сервер

Редактор сценария — это форма, секции которой идут в порядке стадий: датасет и индекс →
retrieval → rerank → context → generation → кэш → нагрузка и повторы → таймауты →
метрики и вывод. Рядом вкладка **YAML** с тем же содержимым: правка в любой вкладке
отражается в другой. Неизвестные форме ключи сохраняются как есть (round-trip), чтобы
вставленный YAML не терял полей.

Форма собрана вручную, а не сгенерирована из JSON Schema. Причины, по коду:
`run.load.concurrency` в `model_json_schema()` отсутствует (`LoadConfig` с
`extra="allow"`), `dataset.source` и `run.load.type` объявлены как `str`, а не `Literal`,
`storage.backend.type` допускает `pgvector`/`milvus`/`weaviate`, реализован только
`qdrant`, а `retrieval.sources[].params` — свободный dict, где по `kind` читаются разные
ключи (`ef_search`, `backend_ref` / `k1`, `b`). Схема и значения по умолчанию берутся с
сервера (`GET /v1/meta/scenario`) для подсказок «по умолчанию 60», enum и описаний, но
раскладка и ограничения «что реально реализовано» — в UI.

Валидность: форма проверяет только типы и обязательность и показывает несколько живых
подсказок (глубина финального списка, `chunk_overlap < chunk_size`, сумма бюджетов
стадий против `total_ms`). Всё остальное — ответ сервера на **Проверить** = dry-run
(`POST /v1/runs` с `dry_run: true`), который возвращает либо 422 со списком проблем,
либо отчёт preflight с предупреждениями. Отдельной validate-ручки по рамке 38 нет, и UI
её не просит.

Проблемы привязываются к полям по `path`. Сейчас это невозможно: ошибки схемы — это
`pydantic.ValidationError` с `loc` (у model-валидаторов `loc` пустой), а `Issue.where`
— это `qrels/test.tsv:7` или `target default (chunks_v1)`, не путь конфига. Поэтому
UI требует от 28 единый формат (см. «Что нужно от API»): `path` для ошибок конфига,
`where` для проблем датасета и индекса. Проблемы без `path` показываются в секции
«Датасет и индекс» и в общей панели «Проверка».

### 4. Запуск — это сохранить, проверить, подтвердить, поставить в очередь

Кнопка **Запустить** в редакторе делает по порядку: сохраняет сценарий (прогон всегда
ссылается на сохранённую версию), делает dry-run, при ошибках останавливается и
показывает их, при предупреждениях (`index.not_green`, `qrels.no_relevant`, …)
спрашивает «Запустить всё равно?», затем `POST /v1/runs` и переход на `/runs/<id>`.

Preflight выполняется дважды: при постановке в очередь (иначе 422 и в очередь ничего не
попадает) и при старте задачи, потому что пока прогон ждал, индекс могли пересобрать.
Во втором случае задача становится `failed` с тем же списком проблем — это требование к
29.

Из списка сценариев можно запустить несколько сразу: они встают в очередь в выбранном
порядке, по одному dry-run на каждый; те, что не прошли, остаются в диалоге со своими
ошибками, остальные запускаются. Так ставится серия S0–S5 на ночь.

### 5. Один URL прогона от 202 до результата

`POST /v1/runs` отвечает 202 с `id`, и этот `id` — навсегда идентификатор прогона в
реестре (30). Страница `/runs/<id>` работает во всех состояниях. Состояния задачи из 29:
`queued → running → completed | failed | cancelled`. Внутри `running` UI показывает
фазы, которых у ядра нет как событий, но которые выводятся из того, что есть:

| Фаза | Как определяется | Что показать |
|---|---|---|
| Подготовка | задача `running`, события `progress` ещё не было | «preflight, загрузка моделей, индекс BM25» без полосы |
| Запросы | есть `progress("queries", done, total)` | полоса `done / total`, повтор `(done-1) // n + 1` из `repeats`, прошло, осталось ≈ |
| Завершение | `done == total`, задача ещё `running` | «запись summary» |

Для сборки то же с `progress("corpus", …)`, и после 100 % есть ещё последний батч
эмбеддинга и запись метаданных — это «Завершение».

Оценка «осталось» — линейная по средней скорости с момента первого события, с пометкой
«≈»; настоящий `throughput_qps` появится в summary. Живых метрик (p50 по ходу прогона)
нет: ядро сообщает только прогресс, и считать перцентили в процессе прогона значит
тратить CPU, который сейчас измеряется.

### 6. Индекс выбирается из коллекций, embedding берётся из индекса

В схеме сценария нет ссылки на профиль индекса: связь — `storage.backend.endpoint` и
`collection`, а совместимость preflight проверяет по метаданным коллекции (хэш корпуса,
`embedding_model`, `embedding_normalize`, layout). Поэтому в форме секция «Датасет и
индекс» начинается с выбора **коллекции** из списка, который API строит по всем Qdrant
endpoint-ам из конфига сервера (`ragglet serve`; `localhost` тоже годится): endpoint,
имя, статус, датасет, модель, chunking, `points`, когда собрана. Выбор коллекции заполняет
`storage.*` и `embedding.*` (их показываем как «из индекса», с кнопкой «задать вручную»)
и предлагает `dataset`, если он пуст или отличается. Для `storage.mode: sharded`
выбираются несколько коллекций в `backends[]`, и из них же берутся значения для
`params.backend_ref` у источников.

### 7. Секретов в UI нет

В конфиге ключей нет: `generation.api_key_env` — имя переменной окружения сервера. Форма
показывает имя и статус «задана / не задана» из `GET /v1/stand`. Redis- и Qdrant-URL —
обычные поля; рядом с Redis-URL подсказка, что пароль в URL попадёт в snapshot прогона.

### 8. Опрос, не стриминг

Активные страницы опрашивают сервер раз в 1–2 с (`GET /v1/runs/<id>` без тяжёлых полей),
списки — раз в 10 с, лог — по смещению. SSE/WebSocket не нужны одному пользователю и
усложняют 28; добавить можно позже, не меняя страниц.

### 9. Экспорт — как есть

YAML сценария скачивается тем же текстом, что хранится в библиотеке. Артефакты прогона
отдаются файлами реестра без преобразований (`summary.json`, `per_query.repeat0.parquet`,
…) и одним zip. Экспорт графиков (PNG/SVG для статьи) — ragglet-32.

## Экраны

### Стенд `/`

Одна страница, четыре блока, сверху вниз:

1. **Сейчас.** Карточка активной задачи: тип (прогон / сборка), имя сценария или
   профиля, фаза, полоса прогресса, прошло, осталось ≈, кнопка «Отменить», ссылка на
   страницу. Если стенд свободен — «Стенд свободен» и кнопки «Запустить сценарий»,
   «Собрать индекс».
2. **Очередь.** Список ожидающих задач по порядку: позиция, тип, имя, когда поставлена,
   «Убрать из очереди». Перестановка — вне скоупа.
3. **Сервисы.** Qdrant (URL, доступен, версия, число коллекций), Redis (URL, доступен,
   версия), вычисления (`device`, CPU, потоки), код (`commit`, Python), переменные
   окружения для генерации (`OPENAI_API_KEY`: задана / нет). Это то, что
   `environment.py` уже собирает в `manifest.env`, только живьём.
4. **Недавние.** Последние 5 прогонов (статус, сценарий, когда, nDCG@10, p95, QPS) и
   последние 3 сборки (статус, профиль, коллекции, когда).

### Сценарии `/scenarios`

Таблица: имя · описание · датасет · коллекция · конвейер (чипы: `single` /
`fanout_merge ×N`, `rerank`, `context`, `generation`, `cache`, `×16` для concurrency,
`×5` для repeats) · последний прогон (статус, дата, nDCG@10, ссылка) · изменён.
Действия строки: Открыть, Запустить, Дублировать, Экспорт YAML, Удалить (с
подтверждением; прогоны остаются, у них есть snapshot). Над таблицей: «Новый сценарий»
(пустой / из YAML), множественный выбор и «Запустить выбранные», поиск по имени и
описанию, фильтр по датасету и тегам.

```
│ Таймауты     │   input_top_k [50]   output_top_n [10]                           │
│ Метрики   ●  │ ▸ Context — выключен                                             │
│              │ ▸ …                                                              │
├──────────────┴──────────────────────────────────────────────────────────────────┤
│ Проверка: 1 ошибка, 0 предупреждений                        ▴ свернуть          │
│  ✕ metrics.quality.k   k=30 exceeds final list depth 10 (rerank.output_top_n)   │
└─────────────────────────────────────────────────────────────────────────────────┘
```

Слева — список секций с точками состояния после проверки (красная — ошибка, жёлтая —
предупреждение). Свёрнутая секция показывает одну строку сводки
(«Retrieval — fanout_merge · 2 источника · rrf k=60»). Выключенная стадия сворачивается
в «выключен». Внизу — панель «Проверка», как Problems в IDE: клик по строке прокручивает
к полю. Вкладка YAML — редактор с подсветкой; ошибки разбора YAML показываются в ней же
и блокируют проверку.

Секции и поля, с тем, что форма делает сверх «поле ↔ ключ YAML». Полный инвентарь
полей, умолчаний и валидаторов — в приложении.

**Датасет и индекс.** Коллекция (из `GET /v1/indexes`); для `storage.mode: sharded |
replicated` — список коллекций в `backends[]` с `id`. `dataset.source` (`local` / `hf`),
`dataset.id` (для `local` — выбор из каталогов, которые знает сервер, для `hf` — repo id),
`dataset.revision` (только `hf`), `split`, `limit`. `embedding.model` / `normalize` —
из индекса, подсвечиваются при расхождении. Живая подсказка: датасет коллекции ≠
датасет сценария.

**Retrieval.** `strategy` (`single` / `fanout_merge`; `cascade` не предлагается — в
рантайме `NotImplementedError`), `top_k`, `async` (показывается только для
`fanout_merge`). Источники — список карточек: `name`, `kind` (`vector` / `keyword`),
`weight`, и по `kind` — `ef_search`, `backend_ref` (выбор из id целей `storage`) или
`k1`, `b`. Для `single` форма показывает ровно один источник и предупреждает, если в
YAML их больше (ядро берёт `sources[0]`). `keyword` при `single` недоступен (валидатор
схемы). Больше одного `keyword` — подсказка «не реализовано». `merge` показывается при
`fanout_merge`: `method`, `rrf_k` (для `rrf`), `deduplicate` (с пометкой, что влияет
только на `interleave`).

**Rerank.** `enabled`, `provider`, `model` (обязательно для `cross_encoder`),
`revision`, `input_top_k`, `output_top_n`. Подсказка: `input_top_k > retrieval.top_k`
не имеет смысла.

**Context.** `enabled`, `policy`, `max_tokens` (с пометкой «оценка по словам»),
`threshold` (только для `threshold` / `adaptive`), `include_metadata`.

**Generation.** `enabled` (требует `context.enabled` — форма включает контекст сама и
говорит об этом), `provider`, `model`, `base_url`, `api_key_env` со статусом переменной
на сервере, `temperature`, `max_output_tokens`, `save.prompt / answer / raw_response`.

**Кэш.** `enabled`; два слоя с собственными выключателями: embedding (`redis`,
`endpoint`, `ttl_seconds`) и retrieval (`memory_lru`, `size`). Пометка у retrieval-слоя:
кэш живёт в процессе прогона, попадания возможны только при `repeats > 1`.

**Нагрузка и повторы.** `run.repeats`, `shuffle`, `seed`, `load.type` (пока только
`closed`), `load.concurrency`, `save_per_query`. `run.artifacts_dir` в форме нет: это
серверный путь, и его назначает реестр.

**Таймауты.** `total_ms`, `retrieval_ms`, `rerank_ms` (при rerank), `llm_ms` (при
generation). Подсказка: сумма бюджетов стадий против `total_ms`.

**Метрики и вывод.** `quality.k` (чипы чисел), `quality.doc` и `quality.chunk`
(чекбоксы из допустимых, у `chunk` только `hit`, `mrr`, `precision`),
`percentiles`, `latency_steps` (чекбоксы `embed`, `retrieve`, `rerank`, `context`,
`generation`, `total`; включённые стадии предлагаются автоматически), `output.format`,
`output.include_debug_fields` (подпись честная: «сохранять текст контекста в per-query»).
Живая подсказка: глубина финального списка `min(top_k, input_top_k, output_top_n)` и
какое `k` её превышает.

Не показываются, но сохраняются в YAML: `version`, `storage.routing` (в прогоне не
используется).

### Индексы `/indexes`

Две вкладки.

**Коллекции** — то, что реально есть в Qdrant на стендовом endpoint: имя · состояние ·
датасет (`source:id`, ревизия, `corpus_sha256` коротко) · модель и ревизия · chunking ·
`points` · собрана (когда, профиль) · последняя сборка (ссылка). Состояния: `готова`
(метаданные полны, `green`), `оптимизируется` (`yellow` и другие не-`green`),
`недособрана` (есть коллекция, нет метаданных ragglet: сборка не завершилась или
коллекция старого контракта — по коду эти случаи неразличимы), `чужая` (нет ключа
`ragglet`, есть другие метаданные). Действия: «Пересобрать» (открывает профиль с этим
`index_profile_id`, если он есть в библиотеке), «Метаданные» (полный JSON). Удаление
коллекций — вне скоупа.

**Профили** — библиотека, как у сценариев: имя · датасет · chunking · модель · цели
(коллекции) · последняя сборка. Редактор профиля — та же конструкция, что у сценария,
секций меньше: Датасет (`source`, `id`, `revision`), Чанкинг (`method`; `chunk_size`,
`chunk_overlap` только для `recursive`, с подсказкой `overlap < size`), Эмбеддинг
(`model`, `revision`, `normalize`, `batch_size`), Хранилище (`mode`; для `single` —
`endpoint`, `collection`; для `sharded` / `replicated` — `backends[]`, `routing.key`),
Параметры индекса (`distance`, `hnsw.m`, `hnsw.ef_construct`).

**Сборка** из редактора профиля: Проверить (dry-run: ошибки датасета, число документов,
хэш корпуса, цели) → диалог подтверждения: «Будут пересозданы: `chunks_v1` на
`localhost:6333` — существует, 9 696 points, собрана 24.10, её используют сценарии
`nfcorpus_hf`, `nfcorpus_rerank`» → Собрать → 202 → `/builds/<id>`. Данных «существует
ли коллекция и кто её использует» в `BuildResult` нет, их добавляет API (см. ниже).

**Страница сборки `/builds/:id`** — младшая сестра страницы прогона: состояние, фазы
(подготовка: датасет и модель; документы `done / total`; завершение: последний батч и
метаданные), лог, результат (цели, документы, записанные метаданные), ошибка. Действия:
Отменить, Открыть профиль. Упавшая сборка оставляет коллекцию без метаданных — страница
говорит об этом прямо и предлагает пересобрать.

### Прогоны `/runs`

Таблица реестра: состояние · сценарий · когда (старт) · длительность · датасет ·
коллекция · nDCG@k · Recall@k · p50 · p95 · QPS · таймауты % · теги. `k` для колонок —
переключатель над таблицей (по умолчанию 10, если есть в прогоне). Активные прогоны
закреплены сверху. Фильтры в URL: состояние, сценарий, датасет, коллекция, тег, период,
текст. Сортировка по любой колонке. Чекбоксы строк есть уже сейчас, но единственное
действие с ними — «Сравнить» — отключено с подписью «ragglet-32».

Колонки сводки должен отдавать сам список (`GET /v1/runs`), а не UI, читая каждый
прогон, — это требование к реестру.

Шапка одинакова во всех состояниях: сценарий (ссылка на сохранённый, если он ещё есть;
иначе «сценарий удалён», snapshot остался), `id`, состояние, время постановки / старта /
конца, длительность, датасет, коллекция, теги. Действия: **Отменить** (пока `queued` /
`running`), **Повторить** (`POST /v1/runs` с тем же snapshot — новый прогон в тех же
условиях), **Открыть как сценарий** (новый сценарий из snapshot), **Скачать** (zip или
отдельные файлы).

Тело по состояниям:

- **В очереди** — позиция и что впереди (с прогрессом текущей задачи), отчёт preflight
  на момент постановки, вкладки «Условия» и «Конфиг».
- **Выполняется** — фаза (решение 5), полоса, прошло, осталось ≈, предупреждения
  preflight, хвост лога с автопрокруткой. Вкладки «Условия», «Конфиг», «Лог».
- **Готово** — все вкладки, по умолчанию «Обзор».
- **Ошибка** — красная плашка с классом и сообщением исключения и `qid`, на котором
  упал прогон (ядро добавляет его в `__notes__`), «подробности в логе». Если успели
  записаться per-query повторов — «частичные результаты: повторы 0–1» и вкладка
  «Запросы» по ним; summary при падении не пишется, поэтому «Обзора» нет.
- **Отменён** — то же, с «отменён в 12:40, выполнено 420 / 969».

Вкладки готового прогона:

**Обзор.** Переключатель `k` (из `metrics.quality.k`). Плитки: nDCG@k, Recall@k, MRR@k
(doc-уровень; если выбранной метрики в прогоне нет, плитки нет), p50 и p95 `total`, QPS,
исходы (`ok · timeout · error`), доля попаданий кэша (только для включённых слоёв,
`emb_hit_rate` и `ret_hit_rate` из ragglet-22).
Под числом — `± std` и число повторов из `summary.aggregate`. Карточка условий (датасет,
индекс, окружение, предупреждения preflight). Полоса задержек по стадиям (p50 каждой
стадии из `metrics.latency_steps`; стадии без значений не рисуются). График «качество
по k» для метрик doc-уровня, с разбросом по повторам. Таблица повторов — чтобы разницу
«холодный / тёплый» было видно сразу.

**Качество.** Таблица метрика × k, уровни `doc` и `chunk` (если есть), ячейка —
`mean ± std` по повторам, раскрытие — значения по повторам. График метрика(k). Подсказки
с определениями из `docs/metrics.md`. Строка «промахи при k: N запросов (hit@k = 0)» —
ссылка на вкладку «Запросы» с фильтром. `doc_short@k_rate` — сколько запросов получили
список короче k.

**Задержки и нагрузка.** Таблица стадия × перцентиль по повторам и агрегат. Распределение
`lat_total_ms` (гистограмма или CDF, повторы наложением). Линия времени: `t_start_ms` →
`lat_total_ms`, точка — запрос, цвет — исход; на ней видно прогрев и кэш, не читая CSV.
Пропускная способность и исходы по повторам: `wall_ms`, `throughput_qps`, счётчики и
доли, `timeout_stage_counts`, `concurrency` из конфига. Кэш: `emb_hit_rate`,
`ret_hit_rate` по повторам. Всё, кроме таблицы перцентилей, требует per-query; если
`save_per_query: false`, эти блоки заменяются подписью.

**Запросы.** Таблица по повтору (переключатель): `qid`, текст (обрезан), исход,
`timeout_stage`, `lat_total_ms`, задержки стадий (столбцы включаются), `doc_ndcg@k`,
`doc_recall@k`, `doc_hit@k`, ранг первого релевантного (сервер считает из
`final_doc_ids` и `truth_ids`), `n_docs`. Фильтры в URL: исход, «промах при k», `lat_total
> X`, текст. Клик по строке — панель «Запрос»: текст; релевантные документы (`truth_ids`,
оценки из qrels датасета, заголовки); выдача: ранг, `chunk_id`, документ, релевантен ли,
rerank-score (если был), попал ли в контекст, заголовок и текст чанка; ответ генерации
(если была). Чего в per-query нет и UI не обещает: score retrieval, источник
(`vector`/`keyword`), флаг попадания кэша у конкретного запроса.

**Условия.** `manifest.json` структурно: датасет (`source:id`, ревизия, хэши, split,
число запросов), индекс (`profile_id`, `built_at`, модель и ревизия, chunking, `params`:
`vector_size`, `distance`, `hnsw`, `build_env`), rerank (ревизия), окружение (`commit`,
Python, `system`, `compute`, `services`: версии и статус Qdrant, `points`,
`indexed_vectors`, Redis). Предупреждения preflight на момент старта. Переключатель
«JSON». Здесь же в будущем встанет «сравнимо с…» из `compare_runs` (классы `data` /
`config` / `env` уже есть в ядре).

**Конфиг.** `scenario.snapshot.yaml` только для чтения, «Открыть как сценарий». Пометка,
если сохранённый сценарий с тем же именем изменился после прогона (по `updated_at`
файла).

**Лог.** stdout/stderr процесса задачи из 29, с автопрокруткой на активном прогоне,
поиск, скачать. У упавшего прогона traceback вверху.

**Файлы.** Список артефактов с размерами и ссылками, zip.

## Что нужно от API

Формат проблем — общий для всех ответов 422 и для предупреждений:

```json
{
  "title": "Index is not compatible with scenario 'nfcorpus_rerank'",
  "hint": "Rebuild the index: ragglet index build <index_profile.yaml>",
  "issues": [
    {"code": "index.not_green", "severity": "warning", "path": null,
     "where": "target default (nfcorpus_v1)", "message": "collection status is yellow: …"},
    {"code": "config.value_error", "severity": "error", "path": "metrics.quality.k",
     "where": null, "message": "metrics.quality.k=30 exceeds final list depth 10 (rerank.output_top_n)"}
  ]
}
```

`path` — dotted-путь конфига для ошибок схемы (из `loc` pydantic; для двух
model-валидаторов с пустым `loc` — `generation.enabled` и `metrics.quality.k` — путь
задаёт 28 по сопоставлению), `where` — как в `Issue` сейчас. Ошибка разбора YAML —
`config.yaml` с номером строки в `where`.

| Проверка сборки | `POST /v1/builds` `{profile, dry_run: true}` | `BuildResult` плюс по каждой цели: существует ли коллекция, `points`, `built_at`, и какие сценарии библиотеки её используют (ядро этого не знает: dry-run сборки к Qdrant не подключается) | 28 |
| Сборка | `POST /v1/builds` → 202; `GET /v1/builds/{id}` | как прогон: состояние, фазы, `progress corpus`, лог, результат (`targets`, `documents`, метаданные), ошибка | 28, 29 |

Нефункциональные требования:

- `id` прогона — имя его каталога `<name>_<UTC>`, выдаётся при 202 (у сборки каталога
  нет, её `id` назначает 29); состояние, времена, ошибка и лог живут в реестре и
  менеджере, а не выводятся из каталога (в артефактах их нет, и «идёт», «упал», «убит»
  по каталогу неразличимы).
- Опрос состояния — дешёвый: без чтения summary и per-query.
- Времена в UTC ISO 8601, UI показывает локальные.
- UI раздаётся самим API-сервером как статика (один origin, один контейнер в 34);
  в разработке — dev-сервер с прокси на API.

### Что стоит добавить в dry-run ядра (мелкое, в 28)

Сейчас эти ошибки проявляются уже после создания каталога прогона, как сбой задачи с
трейсбеком, а не как 422. UI-флоу «Проверить → Запустить» выигрывает, если они ловятся
в preflight: `retrieval.strategy: cascade` и больше одного `keyword`-источника
(`NotImplementedError` на первом запросе), неизвестный `params.backend_ref` (`KeyError`),
недоступный Redis при `cache.embedding` (сейчас проверяется только в
`describe_services`, dry-run его не трогает), `rerank.model` без доступа к Hub. В 38
такое переводить в `ValidationError` разрешено «если понадобится» — понадобилось.

## Рассмотренные альтернативы

- **Форма целиком из JSON Schema.** Отвергнута: схема неполна и шире реализации (см.
  решение 3), списки источников полиморфны по `kind`, и раскладка по стадиям конвейера
  из схемы не следует.
- **Только YAML-редактор с валидацией.** Отвергнут по ragglet-31 («без ручного
  редактирования YAML»); остаётся второй вкладкой.
- **Сценарии в localStorage браузера.** Отвергнуто: теряются, недоступны CLI, не
  коммитятся.
- **Отдельный раздел «Задачи».** Свёрнут в Стенд и страницы прогона и сборки: у
  пользователя две сущности, а не три.
- **Dry-run как задача (202).** Не нужно: он лёгкий, а датасет к моменту прогона уже в
  кэше после сборки индекса.

## Решено при обсуждении

1. **Имя прогона остаётся `<name>_<UTC>`**, оно же — `id` прогона в реестре. Два прогона
   в одну секунду невозможны: менеджер задач (29) выполняет одну тяжёлую задачу за раз.
2. **Endpoint-ы Qdrant — список в конфиге сервера** (`ragglet serve`), в том числе
   `localhost`. `GET /v1/indexes` собирает коллекции со всех endpoint-ов списка.
3. **Предупреждение о «тёплых» повторах** при `shuffle: false` и кэше в форме не
   показывается — лишнее усложнение.
4. **Чистка библиотеки сделана в этом PR:** у `baseline_qdrant_fanout_two_vec.yaml`
   описание приведено к содержимому (hybrid vector + BM25 с кэшем), устаревший
   комментарий в `s1_async_retrieval.yaml` заменён.
