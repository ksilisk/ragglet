# ragglet-32 — Результаты прогона: графики, запросы, условия, сравнение и экспорт

**Коротко.** Вкладки результата, которые в 31 стоят неактивными, наполняются: «Обзор»
получает полосу задержек по стадиям и график «качество по k», появляются «Качество»,
«Задержки и нагрузка», «Запросы» с панелью запроса и «Условия». Список прогонов получает
работающую кнопку «Сравнить», она ведёт на страницу `/compare?ids=a,b[,…]`: плашка
сопоставимости, различия конфига, метрики бок о бок и общие графики. Каждый график
скачивается в SVG и PNG, каждая таблица в CSV. Графики строит ECharts 6. Он грузится
отдельным ленивым чанком, а опции графиков собирают чистые функции из `summary` и
per-query. Цвета задаются токенами в `tokens.css`, в обеих темах. Палитра проверена на
различимость по светлоте и для дальтоников. В Python добавляются две вещи: параметр
`fields` у `GET /v1/runs/{id}/queries`, чтобы распределения задержек не тянули строки
целиком, и `GET /v1/runs/compare` поверх `bench/compare.py`. Реализация идёт двумя PR:
вкладки прогона и экспорт в этом, сравнение — во втором.

## Пример, на котором всё объясняется

Сюжет ragglet-15: помогает ли реранк на nfcorpus. Есть прогон без реранка `nfcorpus_hf`
и новый `nfcorpus_rerank` (3 повтора, concurrency 16). Числа ниже — иллюстрация.

1. **Обзор.** Плитки как в 31. Ниже карточка «Условия» (датасет, индекс, rerank,
   окружение, предупреждение `indexed_vectors = 0`) и «Задержки по стадиям, p50»:
   полоса `embed 146 · retrieve 6 · rerank 160` и отметка `total 318`, под ней таблица
   p50/p95/p99 со строкой «Таймауты по стадиям: rerank 7 (2,2 %)». График «Качество по
   k»: четыре линии (ndcg, recall, hit, mrr) по k = 1, 3, 5, 10 с усами ± std по трём
   повторам. Кнопки «Запросы с таймаутом · 7» и «Промахи при k=10 · 101».
2. **Качество.** Таблица метрика × k для уровня doc: nDCG@10 `0,331 ± 0,004`; по клику
   строка раскрывается в значения трёх повторов. У названия метрики ⓘ с определением из
   `docs/metrics.md`. Строка «список короче k» показывает `doc_short@10_rate` 6 %.
   «Промахи при k=10: 101 / 101 / 100 по повторам» — ссылка на
   `?tab=queries&repeat=0&miss_at=10`.
3. **Задержки и нагрузка.** CDF `lat_total_ms`, три повтора наложением, лог-шкала:
   почти все запросы до 1,2 с, затем ступенька у 6 000 мс, это бюджет `total_ms`, отмечен
   вертикальной линией. Линия времени повтора 0: треугольники таймаутов в первые 3 с —
   холодный cross-encoder. Таблица повторов: `wall`, QPS, исходы,
   `timeout_stage_counts`, concurrency 16.
4. **Запросы**, чип «timeout · 7». Таблица на 7 строк, у всех `rerank` пуст. Клик →
   панель: текст запроса, 38 релевантных документов с оценками и заголовками (первые 10,
   «ещё 28»). Финальный список пуст: запрос без ответа — промах. Ссылка из адресной
   строки идёт в заметки.
5. **Условия.** Датасет с ревизией и хэшами, индекс `nfcorpus_v1` с `build_env`, модель
   реранка с ревизией, окружение, сервисы. Предупреждение: `indexed_vectors = 0` при
   9 696 points — HNSW не построен, поиск идёт перебором.
6. **Сравнение.** В «Прогонах» отмечены `nfcorpus_hf` и `nfcorpus_rerank`, «Сравнить ·
   2» → `/compare?ids=nfcorpus_hf_…,nfcorpus_rerank_…`. Зелёная плашка: «Различаются
   только настройки RAG». Таблица различий: `rerank.enabled`, `rerank.model`,
   `retrieval.top_k`, `timeouts.rerank_ms`, а также `rerank` в manifest (ревизия). Метрики
   бок о бок при k = 10: nDCG `0,315` → `0,331` (+0,016, +5 %), p50 `152` → `318` мс.
   График «качество по k» — по линии на прогон. «Задержки по стадиям» — полоса на
   прогон в тех же цветах стадий, что в «Обзоре».
7. **Экспорт.** У графика «качество по k» меню ⤓ → SVG: файл
   `compare_2runs_quality-k.svg`, светлый, без заголовка, сразу в статью. «CSV» у таблицы
   метрик: одна строка на метрику, колонки — прогоны, числа с точкой.

## Решение

### 1. Графики — ECharts 6

| | ECharts 6.1 (модули) | Plotly.js 3 (basic) |
|---|---|---|
| Размер (min / gzip) | 687 / 237 кБ: line, bar, scatter, custom, grid, tooltip, legend, markLine, dataZoom, Canvas + SVG | 1 120 / 373 кБ, и в basic нет гистограмм |
| Экспорт SVG / PNG | SVG — offscreen-экземпляр с `SVGRenderer` (`ssr: true`) → `renderToSVGString()`; PNG — offscreen с `CanvasRenderer` → `getDataURL({pixelRatio: 2})` | `Plotly.toImage` из коробки |
| Error bars | нет готовых: `custom`-серия, около 30 строк | есть (`error_y`) |
| Темы | опция собирается из токенов, при смене темы `setOption` | то же через `layout` |
| Вид | без чужой панели, оформление полностью наше | modebar и свой стиль, их надо выключать и переопределять |
| Тысячи точек | canvas, `large: true` у scatter | WebGL только в полном бандле |

Размеры замерены esbuild на этом подмножестве модулей. Для сравнения: основной чанк
приложения весит 159 кБ gzip, чанк CodeMirror — 127 кБ. ECharts выигрывает по весу в
полтора раза и не тянет чужой UI. За это платим `custom`-серией для усов и двумя
offscreen-экземплярами при экспорте. Plotly дал бы экспорт и усы даром, но в полтора раза
тяжелее, а его вид пришлось бы переделывать под артборды.

Как устроено:

- **Ленивый чанк.** `web/src/charts/echarts.ts` регистрирует модули (`echarts/core` +
  `use([...])`). `<Chart>` подгружает его через `import()` при первом показе. Плитки и
  таблицы рисуются сразу, график показывает скелет до загрузки чанка.
- **`<Chart option label exportName height>`** — своя обёртка, около 80 строк, без
  `echarts-for-react`. `init` с `renderer: "canvas"`, `ResizeObserver`, `setOption(option,
  {notMerge: true})` при смене опции или темы, `dispose` при размонтировании. Карточка
  графика (`ChartCard`) — заголовок, легенда-подпись и меню экспорта (§10).
- **Опции — чистые функции** `(данные, тема) → EChartsOption` в `charts/options/*.ts`.
  Их тестирует Vitest без DOM. В компонентных тестах `<Chart>` подменяется заглушкой,
  которая выводит число серий и точек.
- **Интерактивность**: подсказка у каждой точки и столбца (`mean ± std`, min–max, n),
  легенда скрывает серии кликом, `dataZoom` по оси времени у линии времени, переключатель
  лог-шкалы у распределения. Больше ничего: ни brush, ни сохранения состояния графика.

### 2. Палитра и оформление

Цвета артборда (`#64748B` slate, `#0D9488` teal, `#2563EB` blue, `#D97706` amber)
валидатор не пропускает. Slate читается как серый (хрома 0,04), а slate и teal у
дейтеранопа почти совпадают (ΔE 5,3 при пороге 8). Поэтому серии берут шесть слотов,
подобранных в OKLCH по светлоте и проверенных скриптом `validate_palette.js` в обеих
темах:

| Слот | Тон | Светлая (L) | Тёмная (L) |
|---|---|---|---|
| 1 | синий | `#285cc2` (0,50) | `#3a6cce` (0,55) |
| 2 | оранжевый | `#f2823b` (0,72) | `#dc7533` (0,67) |
| 3 | бирюзовый | `#0a978b` (0,61) | `#0a978b` (0,61) |
| 4 | фиолетовый | `#6331a0` (0,44) | `#7347af` (0,50) |
| 5 | янтарный | `#e0ab22` (0,77) | `#bb8d07` (0,67) |
| 6 | розовый | `#d4679f` (0,66) | `#c65b93` (0,62) |

- **Светлота.** Соседние слоты чередуются «тёмный — светлый»: в светлой теме разница
  светлоты соседей не меньше 0,11, поэтому полоса стадий и две-три линии различимы и в
  оттенках серого, то есть в ч/б печати статьи. Худшая пара соседей у дальтоников даёт ΔE
  11,0 (порог 8), при обычном зрении — 24,7 (порог 15). Первые три слота проходят проверку
  «все пары» (для точек и наложенных линий) в обеих темах. У тёмной темы полоса светлоты уже (0,48–0,67),
  соседи отличаются на 0,05–0,17, при этом ΔE у дальтоников 11,1. Поэтому светлота —
  не единственный канал (см. ниже).
- **Второй канал.** У линий для каждого слота свой маркер (круг, треугольник, квадрат,
  ромб, скруглённый квадрат, капля) и свой штрих (сплошной, штрих, точки, …). У полосы
  стадий — зазор 2 px и подписи внутри сегментов, у таблиц рядом с графиками — те же
  числа. Оранжевый и янтарный в светлой теме дают контраст ниже 3:1 с белым. Валидатор
  это допускает при подписях или таблице рядом, и подписи с таблицами у нас есть всегда.
- **Закреплённые назначения** (цвет следует за сущностью, а не за местом в списке):
  - стадии в порядке конвейера: embed — 1, retrieve — 2, merge — 3, rerank — 4,
    context — 5, generation — 6. `total` не сегмент: отметка цвета `--text`. Одинаково
    в «Обзоре», «Задержках» и «Сравнении»;
  - метрики: ndcg — 1, recall — 2, hit — 3, mrr — 4, precision — 5, r_cap — 6;
  - прогоны в сравнении: слот — позиция в `ids` (не больше шести);
  - исходы — цвета состояний, а не серий: ok — `--faint`, круг; timeout — `--warning`,
    треугольник; error — `--danger`, ромб.
- **Токены** добавляются в `ui/tokens.css`: `--series-1..6`, `--stage-*`, `--outcome-*` —
  в `:root` и в обоих тёмных блоках (`[data-theme="dark"]` и `prefers-color-scheme`), как
  остальные. Хром графика тоже из токенов: текст `--text`, оси и подписи `--muted`,
  сетка `--border-soft`, подсказка `--tooltip-bg`/`--tooltip-text`, шрифты Plex Sans и
  Plex Mono для чисел. `useChartTheme()` читает их через `getComputedStyle` и
  перечитывает при смене `data-theme` (MutationObserver) и системной темы (`matchMedia`).
  Цветов в обход токенов в компонентах нет — правило 31 сохраняется.

### 3. Данные: откуда что берётся

**Summary.** Разбор ключей уходит из `RunOverview.tsx` в `web/src/results/summary.ts`,
это чистые функции:

| Что | Ключи (`summary.repeats[i]`; агрегат — `<ключ>_{mean,std,min,max}_over_repeats`) |
|---|---|
| качество | `^(doc\|chunk)_(ndcg\|recall\|r_cap\|hit\|mrr\|precision)@(\d+)_mean$` → уровень × метрика × k |
| короткие списки | `doc_short@<k>_rate` |
| задержки | `^lat_(embed\|retrieve\|merge\|rerank\|context\|generation\|total)_p(\d+)$` → стадия × перцентиль |
| кэш | `(emb\|ret)_(hits\|misses\|hit_rate)`, `lat_total_(emb\|ret)_(hit\|miss)_p<P>` |
| исходы и нагрузка | `(ok\|timeout\|error)_(count\|rate)`, `n`, `wall_ms`, `throughput_qps` |
| таймауты по стадиям | `timeout_stage_counts` — словарь в каждом повторе; в агрегате его нет, сумма считается по повторам |

- Одно правило агрегата: `stat(summary, key) → {mean, std, min, max, perRepeat[]}`. При
  одном повторе агрегат может отсутствовать — тогда значения берутся из `repeats[0]`, а
  `std` — `null`.
- **Нет ключа — «—», не 0.** В 31 у старых прогонов (`s0_baseline_rag_20261018T161114Z`,
  без `ok_count`) плитка «Исходы» показывает `0 · 0 · 0`. Это исправляется в этапе 1.
- **Старые поколения** (до ragglet-16/21: `recall@10_mean`, `mrr_mean` без уровня)
  ничем не переименовываются, как и в 30. «Качество» показывает их отдельной таблицей «Метрики
  старого формата: ключи как есть», графиков для них нет. «Обзор» показывает только
  плитки, ключи которых есть.

**Snapshot** (`?include=scenario`, YAML, разбирается тем же `parseYaml`, что в 31) нужен
для: включённых стадий и слоёв кэша (в старых summary `emb_hit_rate = 0` есть и при
выключенном кэше — решение 31), бюджета `timeouts.total_ms` (линия на распределении),
`run.load.concurrency` (у импортированных нет `plan`), `metrics.quality.k`.

**Per-query для графиков задержек** — `GET …/queries?repeat=r&fields=qid,t_start_ms,
lat_*,outcome,timeout_stage,emb_cache,ret_cache&limit=5000` (новый `fields`, раздел
«Требования к API»). Один запрос на повтор: строка около 120 байт, 2 000 запросов — 240
КБ на повтор. Грузится, только когда открыта вкладка «Задержки и нагрузка». Хранится без
срока (`staleTime: Infinity`): результаты завершённого прогона не меняются. 404
`run.no_per_query` (`save_per_query: false`) — подписи вместо блоков.

### 4. Обзор

Раскладка артборда `RunOverview`: плитки (есть) → две колонки «Условия» | «Задержки по
стадиям, p50» → две колонки «Качество по k» | «Повторы».

- **Задержки по стадиям, p50.** Горизонтальная полоса: сегменты стадий в порядке
  конвейера, ширина пропорциональна p50 стадии, подпись в сегменте, если влезает. Отметка
  `total p50` на той же шкале. Подпись под полосой: «сумма медиан стадий не равна медиане
  total: стадии fanout идут параллельно, есть накладные расходы». Ниже — таблица
  стадия × перцентиль (из `metrics.percentiles`) по агрегату и строка «Таймауты по
  стадиям: rerank 7 (2,2 %)» из `timeout_stage_counts`. Выключенные стадии не рисуются, в
  легенде есть пометка «context, generation — выключены».
- **Качество по k.** Линии метрик doc-уровня (что есть в summary), по оси x — k как
  категории (1, 3, 5, 10), шкала 0–1. Усы — ± std по повторам, если повторов больше
  одного, и подпись «усы — std по N повторам». Выбранное в селекторе `k` значение
  отмечено вертикальной линией.
- **Повторы** — таблица 31 без изменений плюс кнопки артборда «Запросы с таймаутом · N» и
  «Промахи при k=K · N» (счётчики повтора 0, ссылки в «Запросы» с фильтром).
- **Условия** — краткая карточка из manifest (тот же форматтер, что вкладка «Условия», §8),
  ссылка «Подробнее →». Появляется в этапе 4.

### 5. Качество

Переключатель уровня `doc | chunk` (chunk — если есть в summary).

- **Таблица метрика × k**: ячейка `mean ± std` (при одном повторе только `mean`), под
  строкой метрики раскрываются строки повторов. ⓘ у метрики — определение и формула из
  `docs/metrics.md`, переведённые и сокращённые в `results/metricInfo.ts` (ru/en). Ниже
  строка «список короче k» — `doc_short@k_rate` в процентах — с пояснением из раздела
  «Граничные случаи» `docs/metrics.md`.
- **График метрика(k)** — тот же построитель, что в «Обзоре», с переключателем уровня.
- **Промахи при k** — по каждому k и повтору `n − hits`, где `hits = round(n ·
  doc_hit@k_mean)`. Это точно: `hit` у запроса — 0 или 1, а запрос без ответа — промах.
  Число — ссылка `?tab=queries&repeat=r&miss_at=k`. Сервер фильтрует `miss_at` по
  `first_relevant_rank > k` — по проверке 30, ровно те же строки.

### 6. Задержки и нагрузка

Сверху — переключатель повтора «все | 0 | 1 | …», он влияет на таблицы и линию времени.

1. **Перцентили по стадиям** — таблица стадия × перцентиль. В режиме «все» ячейка
   `mean ± std` по повторам, иначе — значение повтора. Колонка `n` — сколько запросов
   завершили стадию (из per-query: непустые `lat_<стадия>_ms`; без per-query её нет).
2. **Распределение `lat_total_ms`** — CDF, а не гистограмма: повторы накладываются
   линиями без перекрытия столбиков, перцентили читаются прямо с оси y, ступенька
   таймаутов у бюджета видна сразу. Ось x переключается на лог-шкалу. Вертикальные линии —
   `timeouts.total_ms` и выбранный перцентиль. Повторы — слоты палитры по номеру.
3. **Линия времени** выбранного повтора (в режиме «все» — повтор 0): точка — запрос,
   x — `t_start_ms` в секундах, y — `lat_total_ms`, цвет и форма — исход. Если кэш
   включён — переключатель «раскраска: исход | кэш» (hit/miss слоя `ret`, иначе `emb`).
   `dataZoom` по x.
4. **Пропускная способность и исходы по повторам** — таблица: `n`, `wall_ms`,
   `throughput_qps`, `ok/timeout/error` (число и доля), `timeout_stage_counts` строкой
   (`rerank 7 · total 2`), concurrency и модель нагрузки из snapshot. Подпись из
   `docs/metrics.md`: QPS — только ответы `ok`.
5. **Кэш** (если включён хотя бы один слой) — таблица по повторам: `<слой>_hits`,
   `misses`, `hit_rate`, p50/p95 `lat_total` у попаданий и промахов. Подпись: «доля
   накопительная — hits / (hits + misses) за весь повтор, по счётчикам». С per-query
   рядом рисуется **накопительная кривая** доли попаданий по ходу повтора (запросы по
   `t_start_ms`): на ней виден прогрев. Для `ret` подпись из `docs/metrics.md`: на
   уникальных запросах LRU не попадает.

Без per-query блоки 2, 3, колонка `n` и кривая кэша заменяются подписью «per-query не
сохранялись (`run.save_per_query: false`): доступны только итоги summary».

### 7. Запросы

Раскладка артборда `RunQueries`: строка фильтров → таблица слева, панель запроса справа
(440 px). Уже 1 200 px панель встаёт под таблицу.

**Фильтры и состояние — в URL** под теми же именами, что параметры API, без слоя
перевода: `tab=queries&repeat=0&outcome=timeout&miss_at=10&min_total_ms=1000&q=fava&
sort=-lat_total_ms&offset=50&k=10&qid=PLAIN-1161`. Разбор и сборка — `results/queryParams.ts`.
Умолчания в URL не пишутся. Смена фильтра сбрасывает `offset` и `qid`.

- Строка фильтров: повтор (`repeats` из ответа), чипы исхода «все · ok · timeout · N ·
  error · N» (счётчики из summary повтора), «промах при k=K · N» (`miss_at` = текущий
  `k`, счётчик как в §5), «total > [ ] мс» (число вводится, счётчик — `total` ответа),
  поиск по `qid` и тексту (с задержкой 300 мс), справа «N запросов · сортировка: …».
- **Таблица** — TanStack Table в ручном режиме: сортировка, фильтры и страницы делает
  сервер, библиотека держит колонки, их видимость и состояние сортировки. Страница — 50
  строк, ‹ назад / дальше › как в «Прогонах». Колонки: `qid`, запрос (две строки,
  остальное — в подсказке), исход (чип `timeout · rerank`), `total`, стадии из `columns`
  ответа (видимость — меню «Колонки», по умолчанию включённые стадии сценария), nDCG@k,
  Recall@k, «1-й рел.» (`first_relevant_rank`, `> k` красным), `n_docs`. Клик по
  заголовку — `sort` на сервере, клик по строке — `qid` в URL.
- **Панель запроса** — `GET …/queries/{qid}?repeat=`:
  - шапка: `qid`, чип исхода с `total` мс; текст запроса; строка задержек стадий и
    `t_start`;
  - «Релевантные по qrels · N»: оценка (`grade`) плашкой, `doc_id`, заголовок, ранг в
    выдаче или «> k / не найден». Сортировка — по рангу, затем по оценке. Первые 10, затем
    «ещё N» (в nfcorpus у запроса в среднем ~38 релевантных);
  - «Финальный список · M»: ранг, отметка релевантности (оценка или «·»), `doc_id`
    (`chunk_id` в подсказке), заголовок, rerank-score (если был), «в контексте» (если
    context включён). «Показать текст» раскрывает текст чанка: он уже пришёл в ответе;
  - ответ генерации и текст контекста (`row.answer`, `row.context_text`) — свёрнутыми
    блоками, если есть;
  - честные подписи по `grades` и `texts` (`Availability`): «оценки недоступны:
    датасета нет локально», «тексты недоступны: коллекция пересобрана (built_at …)», и
    всегда: «score retrieval и источник (vector / keyword) в per-query не сохраняются»;
  - «Следующий →» — следующая строка текущей страницы.
- У упавшего и отменённого прогона вкладка есть, если записан хоть один повтор: «частичные
  результаты: повторы 0–1» из `repeats` ответа. 404 `run.no_per_query` — пустое состояние
  с причиной. 422 `request.filter` у старых поколений (нет `outcome`) — чип исхода
  выключен, подпись «в этом формате артефактов нет колонки outcome».

### 8. Условия

`manifest` структурно, карточками `KeyValue` (классы `.kv` артборда), в две колонки:

| Карточка | Что | Откуда |
|---|---|---|
| Датасет | `source:id`, ревизия, `corpus_sha256` и `eval_sha256` (8 знаков, полный — в подсказке), split, limit, запросов | `run.dataset`, `manifest.dataset`, snapshot, `plan` / summary `n` |

| Окружение | commit, Python, платформа, CPU, ядер, RAM, устройство, потоки torch | `manifest.env` |

- «Сравнить с предыдущим прогоном сценария →» — `GET /v1/runs?scenario=<name>&until=<enqueued_at>&limit=2`,
  ссылка на `/compare?ids=<предыдущий>,<этот>` (во втором PR).
- Вкладка есть у всех прогонов, кроме `queued`: manifest пишется до запросов. Без

  карточки из того, что есть в записи и snapshot.

### 9. Сравнение

**Выбор.** В «Прогонах» чекбоксы активны. Выбор хранится в состоянии страницы и
переживает смену фильтров и страниц, но не перезагрузку. Больше шести — остальные чекбоксы
неактивны с подсказкой. «Сравнить · N» активна при N ≥ 2 и открывает
`/compare?ids=a,b,…` в порядке выбора. Первый прогон — базовый.

**Endpoint** `GET /v1/runs/compare?ids=a,b[,…]` (2–6 id):

```python
class CompareRun(BaseModel):
    id: str
    scenario: str
    state: TaskState
    enqueued_at: datetime
    dataset: str
    collection: str
    tags: list[str]
    has_manifest: bool
    summary: RunSummaryOut | None          # как ?include=summary; None — summary нет

class CompareDifference(BaseModel):
    kind: Literal["data", "config", "env"]
    path: str                              # "scenario.rerank.enabled", "env.compute.device"
    values: list[Any]                      # по одному на прогон, в порядке ids; None — ключа нет

class RunCompare(BaseModel):
    runs: list[CompareRun]
    differences: list[CompareDifference]
    quality_comparable: bool | None        # нет различий data; None — у кого-то нет manifest
    latency_comparable: bool | None        # нет различий env.system / env.compute / env.services
    confounders: list[str]                 # прочие env-пути: commit, python, index.build_env.*
```

- **Правило остаётся в `bench/compare.py`** (ragglet-23: «функция — единственная
  реализация правила»). Добавляется `compare_trees(trees) -> list[Spread]` — N-путевое
  обобщение `_diff` с той же семантикой: спускаемся в ключ, только если у всех прогонов там
  словарь, иначе одно различие на этом пути. `compare_runs(a, b)` становится обёрткой над
  ним, и существующие тесты не меняются. Там же `verdict(spreads) -> Verdict` с тремя
  полями ответа. Секции, `IGNORED` и `section_kind` — без изменений.
- **Дерево прогона** — `{"scenario": record.scenario, **manifest}`. `record.scenario` —
  это `cfg.model_dump()`, ровно то, что ядро пишет в `scenario.snapshot.json` (у
  импортированных — сам snapshot). Поэтому сравнить можно и прогон в очереди, хотя без
  manifest. Если manifest нет хотя бы у одного прогона, сравниваются только секции
  `scenario`, а `quality_comparable` и `latency_comparable` равны `null`: сравнить
  `None` с manifest значило бы объявить датасеты разными без оснований.
- Ошибки: меньше двух, больше шести или повторяющиеся id — 422 `request.compare`;
  неизвестный id — 404 `run.not_found`. Маршрут объявлен в `routers/runs.py` **до**
  `GET /runs/{run_id}`, иначе `compare` уйдёт туда как id (тест на это есть).

**Страница `/compare?ids=…&k=10`** (своя страница, не вкладка — реестр вкладок прогона не
трогается):

1. **Шапка** — прогоны чипами с цветом слота: сценарий (ссылка на прогон), состояние,
   датасет, коллекция, когда. У каждого «×» — убрать из `ids` — и «сделать базовым».
2. **Плашка сопоставимости** по `verdict`, тексты в i18n:
   - всё сопоставимо — «Различаются только настройки RAG: разница метрик относится к ним»;
   - `quality_comparable: false` — «Датасеты разные — качество несравнимо» и пути `dataset.*`;
   - `latency_comparable: false` — «Окружение разное — задержки несравнимы» и пути;
   - `confounders` — «Разный код или окружение сборки индекса — часть разницы может быть
     от них»;
   - `null` — «У прогонов X нет manifest: данные и окружение не проверить, сравнение
     только по конфигу».
3. **Различия** — таблица `путь | прогон 1 | прогон 2 | …`, сгруппирована по классам
   (config, data, env), ячейки, отличные от базового, выделены. Путь без префикса
   `scenario.`, а секция видна по группе. Значения — компактный JSON. Группа env
   свёрнута, если в ней только `points` / `segments` / `indexed_vectors`.
4. **Метрики бок о бок** — выбор `k` (общие k всех прогонов). Строки: doc@k (ndcg, recall,
   r_cap, hit, mrr, precision), p50/p95/p99 total, p50 по стадиям (раскрываются), QPS,
   `wall`, timeout/error rate, доли кэша. Колонки — прогоны, `mean ± std`; у небазовых
   Δ к базовому: абсолютная и в процентах. Если |Δ| не больше суммы std двух прогонов,
   Δ серая с подсказкой «в пределах разброса повторов». Это не тест значимости, только
   честная подпись.
5. **Графики**: «Качество по k» — линия на прогон (цвета слотов, маркеры и штрихи),
   метрика — селектор (по умолчанию ndcg), усы std. «Задержки по стадиям» — полоса на
   прогон (строка = прогон), сегменты в цветах стадий, перцентиль — селектор p50/p95/p99,
   отметка total.

Минимум два прогона, максимум шесть: столько различимых слотов палитры, и при N-путевом
`compare_trees` больше двух ничего не стоит.

### 10. Экспорт

- **График**: меню ⤓ в шапке карточки → «SVG» / «PNG». Отдельный экземпляр ECharts с
  той же опцией, без анимации, размером как на экране. SVG — `SVGRenderer` + `ssr`, PNG —
  canvas с `pixelRatio: 2`. Экспорт всегда в **светлой теме на белом фоне**, в чём бы ни
  был открыт UI: файлы идут в статью. Заголовка в картинке нет (подпись к рисунку
  делается в статье), легенда и подписи осей есть. Шрифт Plex Sans: в PNG он уже загружен
  страницей, в SVG указан `font-family` с запасными `system-ui, sans-serif`. Имя файла —
  `<run_id>_<график>.svg`, на странице сравнения — `compare_<N>runs_<график>.svg`.
- **Таблица**: кнопка «CSV». Значения машинные: колонки — ключи summary (`doc_ndcg@10`),
  точка как десятичный разделитель, без разделителей тысяч, `mean`, `std`, `min`, `max`
  отдельными колонками, UTF-8, RFC 4180. У таблицы запросов CSV — весь отфильтрованный
  набор, а не страница: клиент проходит страницы `limit=5000` с теми же фильтрами.
- **Сравнение**: CSV таблицы метрик (строка — метрика, колонки — `<id>_mean`, `<id>_std`)
  и CSV различий.
- Больше ничего: ни отчётов, ни PDF, ни LaTeX-таблиц.

Сборка CSV — `results/csv.ts` (экранирование, числа), скачивание — `Blob` +
`<a download>`.

## Требования к API (Python в этой задаче)

Параллельных сессий по API нет, правки — здесь. После каждой — `npm run gen:api`,
`schema.d.ts` в том же коммите.

   - `fields` — колонки строки через запятую. Незнакомые молча пропускаются: `columns`
     ответа говорит, что есть. Без `fields` — как сейчас;

2. **`GET /v1/runs/compare?ids=`** — §9. `bench/compare.py`: `Spread`, `compare_trees`,
   `verdict`; `compare_runs` — обёртка. `api/schemas.py`: `CompareRun`,
   `CompareDifference`, `RunCompare`. Новый код проблемы `request.compare`.

Остальное уже есть. Пожелания из «Требований к API» 31 (422 в OpenAPI, 201, описания
полей) 32 не нужны.

## Отклонения от артбордов

- **Палитра** — проверенные слоты §2 вместо `#64748B` / `#0D9488` / `#2563EB` /
  `#D97706`: те не проходят проверку на дальтонизм и светлоту.
- **«Качество по k» — линии, а не группы столбиков.** Четыре-шесть метрик на четырёх k —
  это до 24 столбиков. Линия показывает рост recall и hit с k, а усы на ней читаются. На
  странице сравнения линии по прогонам тоже читаются, столбики — нет.
- **Полоса стадий** получает отметку `total` и подпись, что сумма медиан стадий — не
  медиана total.
- **Пагинация «Запросов»** — «‹ назад / дальше ›», как в «Прогонах», а не «1 2 3 … 33».
- **«Релевантные по qrels»** — первые 10 и «ещё N»: в nfcorpus их десятки, артборд
  нарисовал один.

## Тесты (критерий приёмки)

`npm run check` (свежий `schema.d.ts`, `tsc`, ESLint), `npm test`,
`uv run --extra dev pytest -q -m "not integration"`.

**Vitest, чистые функции:**

1. `summary.ts` на фикстурах из настоящих summary: `nfcorpus_hf_20261024T180917Z` (1
   повтор), `s0_baseline_rag_20261018T161114Z` (5 повторов, без `ok_count`),
   `s2_rerank_20260616T182313Z` (старые `recall@k_mean`, без manifest). Проверяется:

   0, сумма `timeout_stage_counts` по повторам, промахи `n − round(n·hit)`.

   полосы стадий без выключенных, CDF монотонна и кончается на 1, у линии времени цвет и

   сбрасывает `offset` и `qid`.

## Рассмотренные альтернативы

- **Plotly.js** — экспорт и усы из коробки, но 373 кБ gzip против 237 у ECharts, и в
  basic нет гистограмм. Свой modebar и стиль пришлось бы выключать и перекрашивать.
- **Observable Plot / Recharts** (SVG в DOM, экспорт SVG тривиален) — меньше по весу, но
  слабее интерактивность (подсказки, скрытие серий, зум) и медленнее на десятках тысяч
  точек линии времени. PNG пришлось бы растеризовать самим. 15 и 31 сузили выбор до
  ECharts и Plotly.
- **`echarts-for-react`** — лишняя зависимость ради 80 строк, и она прячет `dispose` и
  экземпляр, нужный для экспорта.
- **Гистограмма `lat_total_ms`** вместо CDF — повторы наложением перекрывают друг друга,
  а ширина корзин меняет картину.
- **Вердикт сопоставимости на клиенте** — тогда правило ragglet-23 жило бы в двух местах.
- **Сравнение вкладкой страницы прогона** — у страницы один прогон в URL, а сравнение
  N-местное, ему нужна своя страница.
- **Per-query для графиков без `fields`**, страницами по 1 000 строк: 2 000 запросов × 5
  повторов — 10 запросов и около 4 МБ ради шести колонок.
